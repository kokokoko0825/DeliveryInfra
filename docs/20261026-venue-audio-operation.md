# 会場音声の運用実装

## 目的

PoCで確認したDataChannel PCM・STUNの経路を、マイク送信画面から運用できる形にする。実機での音響遅延を測るまでは、本番利用可能とは判定しない。

## 実装内容

- マイク送信画面にある「会場スピーカーにも送信」スイッチを維持し、個々のマイク端末から会場送信を選べる。
- IVSには配信用処理が有効なマイクトラックを送り、会場には同じ物理入力から複製した低遅延トラックを送る。
- 会場音声はDataChannel PCM、STUNのみで送る。Room IDを `venue-live` に分け、PoC用セッションと混在させない。
- 会場用スピーカー画面から音声トラック方式を外し、PCMに固定する。
- 会場音声の接続APIを音声担当・管理者だけに許可する。
- 最大3マイク・最大5スピーカーを仕様に記録し、全マイクを全スピーカーで同時に再生する。
- スピーカーの音量は各端末の音量ボタンで調整する。
- WebRTCの初回接続が失敗してもマイク送信セッションを維持し、自動再接続を続ける。送信キューはPCM約40ms分を上限として、それ以上は古い音声を落として遅延を抑える。

## 同一マイク入力と音声処理

同じ物理マイクを配信と会場へ同時送信する構成は実現できる。現行実装はマイク取得中の要求を共有し、一度だけ入力を取得する。IVSには元トラック、会場には同じ入力源を参照する複製トラックを使うため、配信開始と会場スイッチの操作が重なっても別々のマイク取得を始めない。

W3C Media Capture仕様では複数のMediaStreamTrackが同一入力源を共有し、異なる制約を持つことができる。会場トラックにはエコーキャンセル・ノイズ抑制・自動音量調整を無効にする制約を適用し、`getSettings()` で3項目すべてが無効と確認できた場合だけ送信を始める。ブラウザが個別設定に対応できない場合、会場送信はエラーにする。IVS側の処理は既存のまま維持する。実際に端末がどのように処理するか、配信の映像音声同期と会場遅延が許容範囲かは実機で確かめる。

## 確認状況と運用判定

変更後の全テスト（521件）、型チェック、lintを通過した。Venueテストでは、全初回接続が失敗しても再接続後に接続完了になること、送信キューが閾値を超えるとパケットを落とすことを確認する。全体ミューテーションテストはGitHub Actionsのpush検証で再実行する。

これらの自動テストは実機での音質・遅延・ハウリングを保証しない。iOS Safari・Android Chromeなど実際に使う端末で、配信音質、映像との同期、会場音響遅延、ハウリングを測定する。実機で会場音響遅延を測定し、目標50ms以下・上限60msを確認するまで、本番利用可能とは判定しない。

実機確認では、まず1マイク・1スピーカーで配信と会場送信を同時に有効化し、音が両方に届くこと、配信の映像音声同期、会場音響遅延、音割れ・ハウリングを記録する。その後、複数マイク・複数スピーカーへ広げる。
