# 会場音声の運用設計と確認状況

## 目的

PoCで音声到達を確認した DataChannel PCM・STUN の経路を、マイク送信画面から運用できる形にする。[Web Audio 分岐設計提案](./20261027-venue-audio-web-audio-design-proposal.md) に沿う新経路の実機検証は未完了であり、音響遅延と配信音質を確認するまでは本番利用可能とは判定しない。

## 従来経路と新設計

- マイク送信画面にある「会場スピーカーにも送信」スイッチを維持し、個々のマイク端末から会場送信を選べる。
- 物理マイクを1回だけ取得し、Web Audio で会場用と配信用に分岐する。会場側は配信用 DSP を通さず既存の AudioWorklet へ、配信側だけはアプリの DSP と `MediaStreamAudioDestinationNode` を通して IVS Stage へ送る。会場スイッチを切っても配信は続ける。
- 会場音声はDataChannel PCM、STUNのみで送る。Room IDを `venue-live` に分け、PoC用セッションと混在させない。
- 会場用スピーカー画面から音声トラック方式を外し、PCMに固定する。
- 会場音声の接続APIを音声担当・管理者だけに許可する。
- 会場送信は最大3マイク・最大5スピーカーを対応目標とし、有効な全マイクを各スピーカーで同時再生する。配信側は既存仕様の最大5マイクを維持する。
- スピーカーの音量は各端末の物理音量ボタンで調整する。iPhone は消音モードを解除し、利用者の操作で再生を開始する。音が出ない場合は出力先と再生状態も確認する。
- WebRTCの初回接続が失敗してもマイク送信セッションを維持し、自動再接続を続ける。送信キューはPCM約40ms分を上限として、それ以上は古い音声を落として遅延を抑える。

## 同一マイク入力と音声処理

従来実装は取得中のマイク要求を共有し、IVS 用の元トラックから会場用トラックを `clone()` していた。新設計ではこの個別トラック処理に依存せず、1つの `AudioContext` と入力ノードから会場・配信へ分岐する。IVS の再接続中も会場送信を維持し、会場接続が失敗しても配信トラックを維持する。共通ミュートは両経路を無音にする。

マイク取得時に `echoCancellation:false`・`noiseSuppression:false`・`autoGainControl:false` を要求する。`getSupportedConstraints()`・`getSettings()` と端末・OS・ブラウザ情報は診断ログに記録する。値が未報告でも、それだけを理由に会場送信を止めない。明示的な `true` も記録・表示し、その条件での測定結果を区別する。要求値と設定値だけで実際の音声処理を断定せず、会場の音響遅延、配信音質と映像音声同期を実機で確認する。

例えば MIC1 と MIC2 が配信中に MIC2 の会場スイッチを切った場合、IVS には両方の音声を送り続け、会場スピーカーでは MIC1 だけを再生する。iOS で `AudioContext` が停止した場合は画面上の再開操作を案内する。

## 確認状況と運用判定

現行経路の変更後には全テスト（521件）、型チェック、lint が通過した。Venue テストでは初回接続失敗後の再接続と、送信キューが閾値を超えたときの古いパケットの破棄を確認した。これらは Web Audio 分岐・配信用 DSP の新設計についての試験結果ではない。

新設計の実装後は、iPhone Safari / Chrome、iPad、MacBook など対象実機で会場音声と配信音声・映像を同時に確認する。会場音響遅延は同じ録音に声の発生音とスピーカー音を入れて測り、RTT で代用しない。目標50ms以下・上限60ms、配信音質、映像音声同期、音切れ、ハウリングを確認するまで、本番利用可能とは判定しない。現時点では新設計の実機測定値はない。

実機確認は1マイク・1スピーカーから始め、配信と会場送信を同時に有効化して双方への到達を記録する。その後、1対多・多対多で各スピーカーに有効な全マイクが聞こえること、スイッチ・共通ミュート・再接続時の動作を確かめる。最大3対5の動作を保証するには、追加端末を用意してその構成で別途検証する。
