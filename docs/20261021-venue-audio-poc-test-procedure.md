# 会場音声 PoC 実機検証手順

この手順は、stgの会場音声PoCで「複数端末へ音声を届けられるか」「同時接続で音が途切れないか」「仕様の遅延目標に近づけるか」を、手元のiPhone 2台・iPad 1台・MacBook 1台で確認するものです。機械ログと耳での確認、音響遅延の実測を区別します。

## 1. 先に知っておくこと

- PoCは同じstgルームを使います。別の人の試験と同時に動かさず、前の参加者を全員「停止」にしてから次の試験を始めてください。
- マイク端末とスピーカー端末の方式は同じにします。片方を「DataChannel PCM」、片方を「WebRTC 音声トラック」にした試験は成立しません。
- PCMを先に試します。PCMはこのPoCで優先して検証する方式だからです。これはPCMが必ず音声トラックより低遅延という意味ではありません。音声トラックはブラウザ内の音声処理が最適化されているため、実機比較で優劣を判断します。
- 画面のRTTは通信の往復時間です。マイク入力からスピーカー出力までの遅延ではありません。
- CSV/JSONログは各端末・ブラウザのIndexedDBに別々に保存されます。マイク1台＋スピーカー3台なら4端末分、2台＋2台なら4端末分を回収します。
- 端末ごとに別のランIDが発行されます。共通ランIDは自動生成されないので、後述の試験記録表で各端末のランIDを試験番号に結び付けます。
- PoCの録音ボタンは、マイクページが取得したマイク入力を録音します。スピーカー端末のデジタル出力を直接録る機能ではなく、遅延を自動計算もしません。録音したマイクがスピーカー音を空気経由で拾える場合に限り、その音もファイルに入りますが、エコーや音響反射が混ざるため校正済み遅延測定にはなりません。

## 2. 準備

### 端末の役割

1対1では、例としてiPhone Aをマイク、iPhone Bをスピーカー、iPadを独立録音役、MacBookをログ確認・補助端末にします。1対3では、マイク1台と残り3台をスピーカーにします。2対2ではiPhone 2台をマイク、iPadとMacBookをスピーカーにします。3対1ではiPhone 2台とiPadをマイク、MacBookをスピーカーにします。

役割を変えるときは、前の試験の全端末で「停止」を押し、停止表示になったことを確認します。スロット競合や前ランの混入を防ぐためです。

### 共通条件をそろえる

1. 4台を同じ家庭内Wi-Fiへ接続する。モバイル回線やVPNは試験中に混ぜない。
2. Bluetoothイヤホン、外部スピーカー、ヘッドホンを外し、実際に使う端末スピーカーを鳴らす。
3. iPhone/iPadでは画面を点灯したままにする。音量を聞き取りやすい安全な位置に設定し、試験中は変えない。最大音量にする必要はない。
4. iPhone/iPadは最初に使うブラウザでPoC URLへログインし、マイク権限を許可する。受信端末では端末の消音設定・ブラウザの再生制限も確認する。
5. 端末名、モデル、OS、ブラウザ、Wi-Fi名、各端末の配置、音量ボタンの位置を記録する。iOS版ChromeはWebKitで動くため「iOS Chrome」として記録し、Android Chromeと同一扱いしない。
6. 人の話し声を使う場合は、マイクから一定の距離（例: 20cm）で、毎回同じ短い文を読む。機械ログ比較中は話者・距離・音量を固定する。

## 3. 1回の試験の共通操作

1. 試験番号を決める。例: `11-PCM-r1` は1対1・PCM・1回目。
2. 試験に参加する全端末で同じ方式を選ぶ。必要ならスロットを固定する（MIC1、SPK1など）。Autoを使う場合も割り当てられた番号を記録する。
3. 先にスピーカー端末で「受信開始」を押す。その後、マイク端末で「接続開始」を押す。iOSの許可ダイアログが出たら許可する。
4. 全端末が「接続中」になり、接続数が期待値になったことを確認する。接続中になる前の状態は試験結果に含めない。
5. 接続後、まず短い試験音声を送る。例: 「試験番号11、これはテストです」を通常の声で話し、スピーカー側で聞き取り、音切れ、遅れて重なって聞こえる反復音がないか記録する。
6. 1分間接続を維持する。多マイク試験では最初に一人ずつ発話して音源を確認し、その後10秒程度、全員が同時に話す。長時間の連続大音量再生はしない。
7. UIに表示される接続状態と統計を記録する。PCMでは各マイクのキュー時間、underflow、overflow、drop、sequence gapを確認する。両方式ともpeer接続数、切断、エラー、送受信量を確認する。
8. マイクとスピーカー全端末で「停止」を押す。止める前に画面に出ているランIDを試験記録表に写す。
9. 端末ごとにログの履歴を更新し、その試験のCSVとJSON manifestをダウンロードする。保存先で端末と試験番号を含む名前に変更する。例: `11-PCM-r1-mic-iPhoneA.csv`、`11-PCM-r1-speaker-iPhoneB.json`。
10. 試験を再実行する場合は新しいランとして開始する。同じランへデータを継ぎ足さない。

## 4. 試験マトリクスと目的

まず各構成のPCMを実施し、その後、同じ端末・同じWi-Fi・同じ配置で音声トラックを実施します。各セルを3回行うのが標準です。初回の接続確認だけは1回でよく、問題が出た条件は修正前後を別ランにします。

| 試験番号 | 構成 | 目的 | 接続数の目安 |
| --- | --- | --- | --- |
| 11 | 1 mic → 1 speaker | 基本経路、権限、再生開始、方式比較の基準 | マイク1 peer、スピーカー1 peer |
| 13 | 1 mic → 3 speakers | 1台から3台への同時fan-out、受信端末ごとの差 | マイク3 peers、各スピーカー1 peer |
| 22 | 2 mics → 2 speakers | 多対多で全マイク音声を全スピーカーへ送る、同時音声の混合 | 各マイク2 peers、各スピーカー2 peers |
| 31 | 3 mics → 1 speaker | 3入力のfan-in、ミックス、PCMの3ストリーム処理 | 各マイク1 peer、スピーカー3 peers |

各構成をPCMと音声トラックで実施すると標準で8条件です。各条件3回なら24ランです。時間が限られる場合でも、11の両方式を3回ずつと、13・22の両方式を最低1回ずつ行ってください。13と22を省略すると、多台数の成立性は判断できません。

### 11: 1対1（最初に行う）

目的は、複雑な条件を入れる前に、端末のマイク権限・音声再生・シグナリング・方式選択が動くか確かめ、方式間の基準を作ることです。PCMを3回、音声トラックを3回行います。接続できない場合は、台数を増やさず、この段階で権限・同じLAN・両端末の方式一致を確認します。

### 13: 1対3

目的は、1台のマイクから複数端末へ同時に直接配信できるか確かめることです。3台のスピーカーすべてで同じ短文が聞こえるかを端末別に記録します。マイク側のconnected peersは3、各スピーカー側は1を期待します。1台だけ無音・切断になる場合は、その端末名、OS、ブラウザを記録し、他の2台の成功と分けて扱います。

### 22: 2対2

目的は、多対多の接続と、各スピーカーで全マイク音声を再生する仕様を確かめることです。最初に各マイクが単独で話し、音源と出力端末を対応付けます。次に両方が同時に話し、両スピーカーで両方の声が聞こえるか確認します。各マイクのconnected peersは2、各スピーカーも2を期待します。PCMでunderflow、drop、peakが増えるかも見ます。

### 31: 3対1

目的は、最大3つの入力ストリームを1つの出力で同時再生できるか確かめることです。3人が一人ずつ話してから、短時間同時に話します。スピーカー側のPCM表示で3つのマイクストリームが見えるか、underflow/overflowや音割れが起きないかを記録します。これは3マイク側の負荷確認で、1対3の代用ではありません。

## 5. 方式の比較方法

### DataChannel PCM

PCMは音声トラックを符号化せず、短いPCMフレームをDataChannelで送る方式です。スピーカー側Workletが最大3入力を合成します。低遅延を狙う本命ですが、フレーム欠落や再生バッファのunderflowが音切れになる可能性があります。CSV/JSONのhealth記録では `sequenceGaps`、`backpressureDrops`、`worklet.<MIC>.underflows`、`overflows`、`queuedMs`、`peak`を見ます。`queuedMs`は受信バッファの状態で、全体の音響遅延ではありません。

### WebRTC 音声トラック

音声トラック方式ではWebRTCが音声を送受信し、ブラウザが内部の音声処理を担当します。接続状態、送受信量、聞こえ方、音切れをPCMと同じ条件で比べます。PCMと同じworklet underflow指標はありません。音声トラックの方が安定する場合もありますが、実測前に優劣を決めません。

### A/B比較を公平にする

- 2方式の間で、端末、Wi-Fi、端末間距離、話す文、話者、音量、試験時間を変えない。
- 方式を変更する前に両端末を停止し、次のランで両端末に同じ方式を設定する。
- 順番の影響を見たい場合は `PCM → 音声トラック → PCM` の順に行う。最後のPCMが最初と大きく違えば、Wi-Fi混雑や端末状態が変わった可能性がある。
- 1回の成功だけで方式を決めない。3回のうち接続失敗・音切れがあった回を残し、都合の悪いランを消さない。

## 6. ログと録音の扱い

### CSV

CSVは各イベント・health sampleを行単位で並べた分析用データです。`record_type=health` の `values_json` に1秒ごとの統計が入ります。表計算ソフトで `run_id`、`elapsed_ms`、`record_type` を使って絞り込みます。列の並びは固定ですが、統計の名前は `values_json` 内にあります。

### JSON manifest

JSON manifestはランのmetadata、イベント、health samples、errors、件数summaryをまとめた機械可読データです。CSVの読み込みで統計名を壊さないため、解析時はJSONも併せて保管してください。

### 各端末のファイルを結び付ける

アプリは端末間で共通IDを発行しません。試験記録表に、試験番号、方式、接続数、各端末の役割/モデル/OS/ブラウザ、画面に出た各ランID、ファイル名、開始のおおよその時刻、聞こえ方を記録します。例:

```text
試験番号: 13-PCM-r2
条件: 1 mic → 3 speakers / DataChannel PCM / home Wi-Fi
MIC: iPhone A, iOS Chrome, MIC1, run ID=...
SPK1: iPhone B, iOS Chrome, SPK1, run ID=...
SPK2: iPad, iPadOS Chrome, SPK2, run ID=...
SPK3: MacBook, macOS Chrome, SPK3, run ID=...
結果: 3台すべて接続。SPK2で一度音切れ。声の明瞭さは良好。
```

### 音響遅延の測定

通信ログだけでは仕様の50ms目標/60ms上限を判定できません。入力の基準音と実スピーカー音が両方含まれた同一の録音を作り、波形の到達時間差を測る必要があります。1対1なら4台目を独立録音役にして、マイク近くの基準音とスピーカー出力の両方が入る位置で録音できます。1対3や2対2では4台すべてが通信端末になるため、独立録音役がありません。正確な多台数の音響遅延判定には別の録音機材または5台目が必要です。マイクページの録音は入力マイクの音を記録するだけなので、スピーカー出力を確実に含む保証はありません。

録音を送る場合は元ファイルを加工せず、録音形式、録音端末、置いた位置、スピーカーの音量、試験番号を一緒に渡してください。今回のPoCは録音波形から遅延を自動算出しません。

## 7. 結果の判定

各ランを次の3項目で別々に判定します。

1. **接続**：期待した全peerが接続状態になり、1分間に切断やエラーがないか。
2. **再生品質**：指定した全スピーカーから意図したマイク音声が聞こえ、音切れ・音割れ・聞き取りにくい反復音がないか。誰がどの端末で聞いたかを書く。
3. **音響遅延**：同一録音の波形で測定できた場合にのみ数値を記録する。50ms以下は仕様目標内、50ms超〜60ms以下は目標未達だが上限内、60ms超は仕様上限超過とする。録音がない場合は「未測定」とする。

接続・再生品質の成功だけで50ms目標を達成したとは結論しません。1方式が失敗した場合も、失敗ログを残してもう一方を同じ条件で試してください。

## 8. 提出するもの

各構成・各方式について、参加した全端末のCSVとJSON manifestを提出してください。加えて、試験記録表、必要に応じて元の音響録音ファイルを添えます。フォルダ名は例として `venue-poc-20261021/` とし、ファイル名の先頭に試験番号を付けます。ログを確認する際は、RTTと音響遅延を混同せず、実機で測れなかった条件を「未測定」として残します。
