# 最大規模の動作確認基盤

## 目的

仕様書上の最大規模で、配信と会場音声が成立するかを本番前に反復確認できるようにする。合格は「同じ条件なら高い確率で動く」根拠を積み上げることであり、すべてのブラウザ・回線・会場での成功を保証するものではない。ブラウザ、OS、端末、Wi-Fi、キャリア回線の差は検証マトリクスと実地試験で残余リスクとして扱う。

## 仕様書から確定できる最大値

- 視聴者: 500人、配信時間: 最大5時間
- 配信入力: カメラ6台、マイク5台、スライド共有1台
- スイッチャー: 制作用11入力とスライド用1入力を受信し、合成した720p/30fpsの番組映像を送信
- 会場音声: 3マイク×5スピーカー、直接WebRTC接続。音響遅延の目標50ms以下、上限60ms
- 配信映像遅延: 1秒未満（目標700ms以下）

## 検証を3層に分ける

### 1. Pull Requestごとの高速検査

既存の単体・統合テストを継続し、最大入力数や接続上限、音声映像の欠落検知、切断・再接続を確認する。これはロジックの退行を検出する層で、実ブラウザや実ネットワークの成功率は示さない。

### 2. ステージングでの実ブラウザ負荷試験

Playwright等でChromiumブラウザを自動起動し、アプリの実際の視聴経路から検証用IVS配信を受信する。視聴者500セッションは複数の負荷ホストに分散し、映像のデコード、音声再生、再接続、受信統計を記録する。単一PCに500タブを開く方式はCPU・メモリが先に限界となり、配信基盤の容量試験にならないため採用しない。

送出素材は時刻カウンター入り映像と識別可能な音声信号を使い、受信側で映像フレームの新しさ、音声到達、音声映像の同期を自動判定する。6カメラ・5マイク・スライドは、最初は合成素材で入力数と合成処理を再現する。合成素材試験に合格した後、実端末を用いた送信確認を別ランで行う。

IVS、CloudFront、Lambda等の実環境の負荷と費用を含むため、試験先はstgに限定する。負荷ランは手動起動、最大500セッション・最大5時間を上限とし、終了時に全セッションを停止する。費用、セッション数、試験ID、使用したビルドを記録する。PRごとのCIでは実行しない。

### 3. 会場音声の実機ベンチ

STUN直結WebRTCとAudioWorkletはブラウザ・端末・Wi-Fiの組合せに依存する。3マイク×5スピーカーを実端末15台で接続する試験を主判定にする。各端末のOS/ブラウザ/機種、Wi-Fiアクセスポイント、帯域・RTT・損失、音声方式、接続状態、PCMの欠落/underflowを記録する。

60ms判定はDataChannel往復時間やworkletキュー長ではなく、音響入力から物理スピーカー出力までを同一クロックで測る。既知の短い音響パルスをマイク入力に入れ、スピーカー出力をオーディオインターフェースの別入力へループバックし、波形相関で遅延を算出する。複数スピーカーは出力ごとに記録する。ループバック治具がない試験結果は遅延判定を「未測定」とする。

まず固定LAN/Wi-Fiの基準条件で成功を確認し、次に帯域制限・RTT・パケット損失を段階的に加え、失敗境界を記録する。無線干渉、端末の省電力、OSの音声バッファ制御はネットワークエミュレーションでは再現しきれないため、実会場と異なる場所での確認も必要。

## 合否と信頼度

- 配信: 500視聴セッションが5時間維持され、全セッションで映像フレームと音声の到達を確認する。音声映像同期と遅延は分位値・最大値を保存し、1秒未満を合格条件とする。
- 会場: 最大3×5接続で全組合せの音声到達を確認。音響遅延は各出力の測定値で50ms以下を目標、60ms以下を上限とする。
- 環境マトリクス: 対応ブラウザの最新版/1つ前、iOS SafariとAndroid Chrome、PC Chrome/Edge、同一Wi-Fiとテザリング/別キャリアを優先する。
- 再現性: 1回の成功を根拠にせず、最大構成を複数回実行し、失敗も含めて保存する。成功率の信頼区間も提示する。例えば独立した30回すべて成功しても、真の成功率が約90%以上と95%信頼で言える程度であり、「99%保証」にはならない。
- 成果物: ビルド識別子、試験条件、端末一覧、ネットワーク条件、開始/終了時刻、セッション数、エラー、遅延分布、同期、音切れ、ログ、合否をJSON/CSVで保存する。

## 実装順

1. 負荷用の時刻入り音声映像素材と、視聴側の自動品質計測ページを作る。
2. Playwrightの負荷ワーカーを作り、少数セッションから段階的に500へ増やす。負荷ワーカー数は計測結果で決める。
3. stg限定の手動実行CLIと安全上限、試験レポート出力を追加する。
4. 3×5会場音声の自動接続制御・ログ収集を整え、オーディオループバック治具を使った実機ベンチ手順を固める。
5. 複数回の結果を確認し、実機イベントで必要な端末・ネットワーク確認の範囲を縮める。

## 現時点の制約

ブラウザ負荷試験は配信経路・サービス負荷を反復確認できるが、500台の物理端末を完全再現しない。会場音声の60msは実端末と出力ループバックなしに判定できない。したがって、基盤の役割は実機イベントの成功を確率的に高めることと、問題が出る条件を事前に特定することに置く。
