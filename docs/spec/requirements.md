
# 限定公開ライブ配信基盤 要件定義書
2026-10-01 · @こうし
## 1. 概要
招待された人だけが視聴できる、遅延1秒未満のライブ配信基盤を AWS IVS Real-Time Streaming で構築する。スマホ最大6台のカメラ映像、最大5台のマイク音声、会場PCのスライド画面共有を管理者PCでスイッチング・合成し、1本の番組映像として配信・録画する。
### 目的とコンセプト
音響や配信の専門知識がなくても、誰でも準備なしで配信と登壇ができることを最優先とする。従来はマイクからラインを取ってミキサーに入れ、スピーカーと配信PCに振り分けるといった配線と設定が必要だった。本システムはその役割をソフトウェアが引き受け、利用者は端末で画面を開くだけで配信できるようにする。
ミキサーなどの音響機材の操作や、ライン配線の知識を利用者に求めない。
映像の切替・音声のミックスは、管理者画面の操作だけで完結させる。
各端末はブラウザで動くことを優先する。ただし、上の目的に必要な場合はネイティブアプリ（スマホ・PC）を使ってよい。

## 4. 機能要件
スイッチング・トランジション・PiP・音声ミックスは管理者PCのブラウザ内で行い、合成済みの1本の映像を視聴者に配信する。これにより遅延1秒未満と、視聴側スマホの負荷を1ストリーム分に抑えることを両立する。
### 4.1 認証
F-AUTH-01 Okta による SSO ログイン（Cognito とのフェデレーション。方式は SAML または OIDC）。
F-AUTH-02 メールアドレス＋パスワードによるログイン。自己サインアップは不可で、管理者が招待したユーザーのみ。
F-AUTH-03 招待時に仮パスワードを記載したメールを送信し、初回ログイン時に変更を必須とする。
F-AUTH-04 パスワード再設定（メールの確認コード）。
F-AUTH-05 パスワードポリシー：12文字以上、英大文字・小文字・数字を含む。5回連続失敗で一時ロック（Cognito 標準）。
F-AUTH-06 セッション有効期限：アクセストークン1時間、リフレッシュトークン12時間（5時間の配信中に切れない設定）。
F-AUTH-07 ログアウト。無効化されたユーザーは次のトークン更新で利用不可となる。
F-AUTH-08 ログイン後、ロールに応じて遷移先を振り分ける（管理者→スイッチング画面へのリンクを表示、カメラ担当→カメラ送信、音声担当→マイク送信、登壇者→スライド共有、視聴者→配信視聴）。
### 4.2 表示名
F-NAME-01 ログイン後に表示名を入力する。前回の表示名を初期値とする。
F-NAME-02 1〜20文字、NGワードを含む名前は不可。重複は許可する。
F-NAME-03 表示名はコメントに表示する。
### 4.3 配信視聴（U-01）
F-VIEW-01 番組映像（720p）を遅延1秒未満で再生する。
F-VIEW-02 配信前・配信終了後は待機画面を表示する。
F-VIEW-03 音量調整、ミュート、全画面表示。スマホの自動再生制限のため、初回は「タップして音声オン」を表示する。
F-VIEW-04 回線断時は自動で再接続する。
F-VIEW-05 同時視聴者数を管理者に表示する（視聴者には非表示）。
### 4.4 コメント
F-CMT-01 コメント送信（1〜200文字）とリアルタイム閲覧。
F-CMT-02 連投制限：1ユーザー3秒に1回まで。
F-CMT-03 NGワードを含むコメントは送信時にブロックする（NGワードは管理者が編集可能）。
F-CMT-04 管理者はコメントを削除でき、全員の画面から即時に消える。
F-CMT-05 管理者は特定ユーザーのコメント送信を停止できる（視聴は継続可能）。
F-CMT-06 途中参加者には直近100件を表示する。
F-CMT-07 コメントログは保存し、管理者がCSVで出力できる。
### 4.5 スライド（U-02 / A-02）
F-SLD-01 管理者がPDFをアップロードする（1ファイル50MBまで、拡張子とMIMEタイプを検証）。
F-SLD-02 タイトル付け、並べ替え、削除。
F-SLD-03 視聴者は一覧から選んでブラウザ内で閲覧し、ダウンロードもできる。
F-SLD-04 配信のページ送りとは同期しない。
F-SLD-05 追加・削除は視聴者の一覧に即時反映する。
### 4.6 カメラ送信（S-01）
F-CAM-01 カメラ担当がスマホブラウザで送信する。720p / 30fps。
F-CAM-02 前面・背面カメラの切替、送信前プレビュー。
F-CAM-03 カメラ映像には音声を含めない（音声はマイク端末から取る）。
F-CAM-04 端末ごとに名前（例：CAM1）を付け、スイッチング画面で識別できる。
F-CAM-05 送信中は画面スリープを防止し、回線断時は自動再接続する。
F-CAM-06 最大6台。7台目は接続を拒否しメッセージを表示する。
### 4.7 マイク送信（S-02）
F-MIC-01 音声担当が、登壇者・質問者の近くでスマホのブラウザで音声を取り込む。同じ音声を配信（IVS）と会場スピーカー（4.8）へ同時に送る。
F-MIC-02 入力レベルメーター、送信側ミュート。
F-MIC-03 端末ごとに名前（例：MIC1）を付ける。
F-MIC-04 送信中は画面スリープを防止し、回線断時は自動再接続する。
F-MIC-05 最大5台。6台目は接続を拒否する。
F-MIC-06 配信用の送信にはモバイル回線か会場Wi-Fiを使う。会場拡声の遅延が増えない方を PoC で決める。
### 4.8 会場スピーカーモード（S-04）
会議室規模の会場で、登壇者・質問者の声を後方の席に補助的に届ける。マイク役のスマホからスピーカー役の端末へ、クラウドを通さず同じWi-Fi（またはテザリング）の中で WebRTC で直接音声を送る。すべてブラウザで実現し、遅延目標に届かない場合だけアプリ化する。大きなホール向けの本格的な拡声（PA）は対象外とする。
F-VEN-01 マイク役（S-02）は、配信用（IVS）とは別に、同じ音声をスピーカー役（S-04）へ直接送る。マイクの音（MediaStreamTrack）を複製して両方に使う。
F-VEN-02 通信方式B（本命）：WebRTC の DataChannel を「順番を待たない・再送しない」設定で使い、音の取り込みと再生は AudioWorklet で行う。音声は無圧縮の PCM（48kHz・16bit・モノラル、約0.8Mbps）または WebCodecs の Opus（10msフレーム）で送る。受信側の待ち合わせ（ジッタバッファ）は自前で 5〜15ms に保つ。
F-VEN-03 通信方式A（次点）：WebRTC の音声トラックで送る。Opus のフレームを 10ms にし、受信側は jitterBufferTarget で待ち合わせを最小にする。方式Bが安定しない端末で使う。
F-VEN-04 予備案：Web（方式B・A）で遅延目標に届かない場合は、マイク役とスピーカー役だけをアプリで包み（Capacitor 等で画面はそのまま流用）、Wi-Fi Aware で直接つなぐ。
F-VEN-05 マイク役とスピーカー役は同じWi-Fiかテザリングの中にいること。接続情報（SDP）の交換は既存の API（Lambda）経由で行い、新しいサーバーは追加しない。同じ LAN 内の直接経路だけを使い、STUN / TURN は使わない。
F-VEN-06 マイク入力からスピーカー出力までの遅延は50ms以下を目標、60msを上限とする。後方の席で生の声とのずれが30〜40ms以内になり、1つの声として聞こえる水準。
F-VEN-07 遅延を縮めるため、マイクのエコーキャンセル・ノイズ抑制・自動音量調整を切り、AudioContext は低遅延設定にする。
F-VEN-08 スピーカー役は1〜2台。スマホ・タブレットのほか、会議室のテレビにつないだ PC の Chrome も使える。会場に流すマイクは最大3台で、スピーカー役の側で混ぜて再生する。中継役は挟まない。
F-VEN-09 会場に流すマイクの選択と、スピーカー役の音量・ミュートは、管理者がスイッチング画面（A-01）から遠隔で操作できる。各端末でもワンタップでミュートできる。
F-VEN-10 ハウリング対策として、音量の上限とハウリングの自動抑制を備える。
F-VEN-11 スピーカー役の画面に、接続状態と実測の遅延を表示する。使用中は画面スリープを防止する（Wake Lock）。
F-VEN-12 運用ルール：スピーカー役は会場の中央から後方の席のそばに置き、マイク役から離す。音量は後方の席で生の声と同じくらいに抑える。マイク役・スピーカー役のスマホは画面をつけたまま給電する。会場では配信（IVS）の音を再生しない（管理者はヘッドホンで確認する）。
### 4.9 スライド画面共有（S-03）
F-SHR-01 会場の発表用PC1台から、ブラウザの画面共有機能でスライドを送信する。登壇者は PowerPoint / Google スライドを普段どおり操作するだけで、配信を意識しない。
F-SHR-02 共有範囲はスライドの表示だけとする。PowerPoint は発表者ビューを使い、スライドショーを映す外部ディスプレイを共有する。Google スライドはスライドショーを表示しているタブを共有する。
F-SHR-03 PC音声（スライド内の動画など）も送信する。PowerPoint は「画面全体＋システム音声」、Google スライドは「タブ＋タブの音声」で共有する（ブラウザの仕様上、ウィンドウ単体の共有では音声を取れない）。
F-SHR-04 送信品質は 1280×720、最大30fps。文字の読みやすさを優先する。
F-SHR-05 同時に共有できるのは1本。登壇者の交代は同じPCのままスライドを切り替えるだけでよく、共有はやり直さない。
F-SHR-06 共有ページには共有中の画面プレビュー、停止ボタン、接続状態、PC音声レベルを表示する。共有開始後はブラウザを最小化しても送信を続ける。
F-SHR-07 共有が途切れた場合はスイッチング画面に警告を出す。管理者はカメラや待機画面に切り替えて対応する。
F-SHR-08 共有ページは自動再接続する。共有の許可だけはブラウザの仕様上、再度の手動操作が必要となる。
F-SHR-09 運用ルール：発表用PCは通知をオフにし、共有する外部ディスプレイにはスライド以外を表示しない。
### 4.10 スイッチング（A-01）
F-SW-01 全カメラ（最大6）とスライド共有画面をマルチビューで同時監視する。接続状態・映像途絶を表示する。
F-SW-02 プレビュー（次に出す画）とプログラム（配信中の画）の2画面構成。
F-SW-03 プレビューで選んだソース・レイアウトを「カット」または「トランジション」でプログラムに切り替える。
F-SW-04 トランジション：カット、ディゾルブ（クロスフェード）、ワイプ。時間は0.3〜2秒で設定可能。
F-SW-05 PiP：メイン1画面＋サブ1画面。サブの位置（四隅）と大きさ（大・中・小）を選べる。スライドをメイン、登壇者カメラをサブにする構成を想定する。
F-SW-06 待機画面（静止画）をソースとして選べる。カメラが途絶した場合に手動で切り替える。
F-SW-07 音声ミキサー：マイクごと（最大5）と会場PC音声の音量・ミュート、全体音量、レベルメーター。カメラ切替とは独立して動作する。
F-SW-08 合成した映像と音声を1本のストリームとして配信用ステージに送る。
F-SW-09 配信開始・終了ボタン。誤操作防止の確認ダイアログを出す。
F-SW-10 配信中の経過時間、同時視聴者数、送信ビットレートを表示する。
F-SW-11 コメント閲覧・モデレーションをパネルで同時に操作できる。
### 4.11 録画・アーカイブ（U-04）
F-REC-01 配信開始と同時に番組映像（スイッチング後の映像）を自動録画する。
F-REC-02 配信終了後、アーカイブとしてログインユーザーが視聴できる。
F-REC-03 管理者はアーカイブのタイトル変更・公開停止・削除ができる。
F-REC-04 アーカイブはダウンロード不可（ストリーミング再生のみ）。
F-REC-05 各カメラ単体の録画は行わない（将来の拡張候補）。
### 4.12 ユーザー管理（A-05）
F-USR-01 メールアドレス（複数可、CSV一括）を入力して招待する。ロールを同時に指定する。
F-USR-02 ユーザー一覧（ログイン方式、ロール、最終ログイン日時）。
F-USR-03 ロール変更、無効化、削除。
### 4.13 運用・デプロイ
F-OPS-01 バックエンドはサーバーレス（Lambda）とし、配信の前後に環境を起動・停止する作業は行わない。
F-OPS-02 配信前の準備は、管理者画面でステージ・Chat の状態を確認するだけとする。
F-OPS-03 インフラとアプリは AWS CDK でデプロイし、本番・検証の2環境を同じ手順で作れるようにする。

### 5.2 可用性・運用
バックエンドはサーバーレス（CloudFront・Lambda・DynamoDB・IVS）とし、常時利用できる。配信時間外もアーカイブとスライドを閲覧できる。
配信中の一時的な回線断は、送信側・受信側とも自動再接続で復旧する。
管理者PCが番組映像を作るため、管理者PCの停止は配信停止に直結する。対策として有線LAN、推奨スペックのPC、予備PCを用意する。
監視：Lambda のエラー、IVS の接続数・ビットレートを CloudWatch のメトリクス画面で確認する。固定費がかかるダッシュボードと常設アラームは置かない。
CloudFront 無料プランの上限（月100万リクエスト・100GB）を超えると速度が落ちる可能性があるため、月1回利用量を確認する。
インフラはコード（AWS CDK）で管理し、同じ環境を再作成できる。本番と検証の2環境を用意する。
### 5.3 セキュリティ
通信はすべて HTTPS / TLS 1.2 以上。映像は WebRTC の暗号化（DTLS-SRTP）。
全画面・全APIでログイン必須。APIはサーバー側でロールを検証する（画面の表示制御だけに頼らない）。
IVS の参加トークンはログイン済みユーザーにのみ発行し、有効期限を短くする。カメラ・マイク・スライド共有の送信権限は、カメラ担当・音声担当・登壇者・管理者にのみ付与する。
スライド・アーカイブは非公開のS3に置き、CloudFront の OAC と署名付きCookieでのみ配信する。
AWS WAF は CloudFront 無料プランに含まれるものを CloudFront に1つだけ適用する（5ルールまで）。ルールは AWS マネージドの共通ルール、既知の不正入力、IPレピュテーション、IPごとのレート制限の4つとする。
API（Lambda 関数URL）は CloudFront からの OAC 署名付きリクエストだけを受け付け、直接のアクセスは拒否する。
保存データは暗号化する（S3、DynamoDB とも AWS 管理キーによる標準の暗号化）。
IAM は最小権限。秘密情報は SSM Parameter Store（SecureString）で管理する。
操作ログ：CloudTrail の証跡を1つ作成し S3 に保存する。管理者操作（配信開始停止、削除、ロール変更）をアプリログに残す。
入力値の検証とXSS対策（コメント・表示名はエスケープして表示）。

## 6. システム構成
IVS Real-Time のステージを「制作用」「スライド用」「配信用」の3つに分ける。カメラとマイクは制作用、会場PCの画面共有はスライド用に送り、管理者PCが合成した番組映像1本だけを配信用に送る。視聴者のスマホは1本だけ受信すればよく、モバイルブラウザの同時受信の制約（3本程度まで推奨）にかからない。
制作用ステージの送信は最大11本（カメラ6＋マイク5）で、1ステージの送信上限12本に収まる。スライドを同じステージに入れると上限ちょうどの12本になり、再接続時に枠が足りなくなるおそれがあるため、スライド用ステージに分ける。管理者PCは2つのステージを同時に受信する。点線はログインやコメントなど、映像以外の通信を表す。

### 8.2 PoC で確かめること
6カメラ＋5マイク（計11の送信）が1つのステージで安定して動くか（上限12）
管理者PCが2つのステージ（計12本）を同時に受信し、合成（トランジション・PiP・音声ミックス）を720p / 30fpsで処理落ちなく再送信できるか
撮影から視聴までの遅延が1秒未満か（実測）
配信用ステージの録画（コンポジット録画）が番組映像として期待どおりに保存されるか。セグメント長とビットレートを設定できるか
iOS Safari・Android Chrome でのカメラ送信とスリープ防止
PowerPoint（外部ディスプレイ＋システム音声）と Google スライド（タブ＋音声）の共有で、文字の読みやすさと動画の音声を確認
Mac の発表用PCでPC音声を共有できるか
Okta と Cognito のフェデレーション、メールユーザーとの混在
CloudFront 無料プランで Lambda 関数URL（OAC）をオリジンにできるか。無料プランの WAF で 4 ルールを設定できるか
OAC 経由の POST リクエスト（本文のハッシュヘッダー）を SPA から問題なく送れるか
東京リージョンで必要な IVS 機能（Real-Time、Chat、録画）がすべて使えるか
会場拡声：方式B（DataChannel＋AudioWorklet）と方式A（音声トラック）の遅延を実測して比べる（拍手の音を1台で録音し、波形のずれを測る）。50ms以下が目標
会場拡声：iPhone Safari・Android Chrome・PC Chrome の組み合わせごとの遅延の違い。PCM と Opus（WebCodecs）の違い
会場拡声：ゲスト用Wi-Fi とテザリングで接続できるか。マイク3台・スピーカー2台で安定するか
会場拡声：マイク役が IVS へ送信しているときに遅延が増えないか（会場Wi-Fi とモバイル回線を比較）
会場拡声：実際の会議室で、後方の席でエコーに聞こえないか、ハウリングしないかを人の耳で確認する
会場拡声（予備案）：Web で届かない場合のみ、Wi-Fi Aware のアプリ版で遅延を測る
