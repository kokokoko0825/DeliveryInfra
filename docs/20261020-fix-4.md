## 例: Chat の一時障害中に配信を停止した場合（R4-01 / R3-14）

| 手順 | 修正前 | 修正後 |
| --- | --- | --- |
| 1回目の停止（SendEvent が4回とも失敗） | DB は ended、500「処理に失敗しました」、監査ログなし | DB は ended、200、`broadcast.stop` の監査ログと `CHAT_EVENT_FAILED` の警告ログが残る |
| 一時障害が1回だけ | 500 | 内部の再試行で通知が届き、200 |
| 管理者がもう一度停止を押す | 200、`broadcast-ended` を再送 | 200、`broadcast-ended` を再送し、監査ログは `broadcast.stop.retry` |

## 見送り・判断

- chatReviewFn の `grantReadWriteData` を `grantReadData` + `PutItem` に絞る案（R4-07 の修正案）は見送った。トリアージの方針は「API Lambda ロール」に限っている。また、`tests/integration/test/infra-api.test.ts` はバンドル済みの `Database` クラスが参照する DeleteItem/UpdateItem も必要な権限として検出する。絞るには、chat-review を `Database` から切り離す変更が要る。
- recording Lambda の SendEvent は変更していない。こちらは失敗すると EventBridge が再試行して回復するので、R2-03 の統合テストもその挙動を前提にしている。
- 停止時の DisconnectUser の失敗は、従来どおり 500 にしている（再実行しても結果は同じ）。審査 Lambda も停止フラグで DENY するので、停止の効果は二重に担保される。
