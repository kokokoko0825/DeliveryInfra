## 詳細

### R3-01 [Medium / 確実] 端末名の重複を回線エラーとして表示する
- 根拠: F-CAM-04 / F-MIC-03。API は他人の同名端末を 409 `DEVICE_NAME_IN_USE` で拒否する（`router.ts:136`）。
- 実装: `classifyError` が判定するのは `DEVICE_LIMIT` と 401/403 だけ。そのため409 `DEVICE_NAME_IN_USE` は `'network'` に分類され、「接続できませんでした。回線を確認して…」と表示される。さらに端末名の初期値は全員が `CAM1` / `MIC1`（`CameraSendPage.tsx:18`、`MicSendPage.tsx:16`）。
- 失敗シナリオ: 2人目の音声担当が初期値の MIC1 のまま送信を始めると回線エラーと表示され、端末名を変えればよいことに気づかずに再試行を繰り返す。
- 修正案: `DEVICE_NAME_IN_USE` 用のエラー種別と文言（例:「MIC1 は他の端末が使用中です。別の端末名を選んでください」）を追加し、テストに加える。

### R3-02 [Medium / 確実] 同じユーザー・同じ端末名の2端末が切断し合う
- 実装: 本人の同名端末は再接続とみなして枠を置き換え、旧参加者を切断する（R1-18）。切断された側は `participant-disconnected` を受けるが、再接続しない扱いなので状態は「送信中」のまま残る。15秒後のハートビートで、`findLease` の deviceId が一致せず 404 になる。`useStageSender` は 404 を受けると `restart()` するので同じ名前で取り直し、今度は相手を切断する。
- 失敗シナリオ: カメラ担当がスマホでタブを開き直す、または予備端末で同じ CAM1 を選ぶ。2端末が約15秒ごとに交互に切断され、番組上の CAM1 の映像が途切れ続ける。
- 修正案: STAGE_LEFT が `participant-disconnected` のときは managed session を止め、「別の端末で同じ端末名が使われたため停止しました」と表示する。ハートビートの 404 は「失効」と「置き換え」を区別する（例: 409 `DEVICE_REPLACED` を返す）。置き換えの場合は再接続しない。

### R3-03 [Medium / 高] アーカイブ再生中の Cookie 失効から復旧しない
- 根拠: U-04 / F-REC-02。Cookie の有効期限は1時間（plan 5章）。
- 実装: Cookie の再取得は React Query の `refetchInterval`（50分）に任せている。これは背面タブやロック中は止まり（`refetchIntervalInBackground` は既定で false）、復帰時は focus を契機に再取得する。hls.js 1.7.3 の `retryForHttpStatus` は 4xx を再試行しないため、セグメントの 403 は即座に致命的エラーになる。ネイティブ HLS（Safari）の経路には error ハンドラがない。
- 失敗シナリオ: iPhone で2時間のアーカイブを再生し、画面をロックして音声だけ聞く。または一時停止のまま1時間以上置く。その後のセグメント取得が 403 になって再生が止まる。Safari では何も表示されない。
- 修正案: hls.js の `ERROR`（`NETWORK_ERROR` / HTTP 403）と video の `error` イベントで `ensureFileCookies` を強制再取得し、現在位置から `hls.startLoad()` を呼ぶか src を再設定する。再生中は visibility 復帰時にも Cookie を確認する。

### R3-04 [Medium / 高] 配信中の番組送信再開が1回の失敗で止まる
- 実装: `live && running && !publishing && !busy` のとき effect が `startPublishing()` を1回呼ぶ。`broadcast.start()` が失敗すると、`stopPublishing()` が managed session の再接続予約ごと止めてしまう。effect の依存値も変わらないため、再試行されない。
- 失敗シナリオ: 配信中に管理者 PC のブラウザを再読み込みしてスイッチャーを起動する。一瞬の回線不調でトークン取得や join が1回失敗すると、トーストが出るだけで番組送信は再開されず、視聴者の映像が止まったままになる。
- 修正案: 配信中の再開では失敗しても session を止めずに managed session の再接続（バックオフ）に任せる。または「番組送信を再開」ボタンと失敗状態の表示を加える。

### R3-05 [Medium / 確実] ショートカットの抑止対象に `<summary>` がない
- 実装: `ACTIVATING_TAGS = ['BUTTON','A']` に SUMMARY が含まれない。そのため「キーボードショートカット」の `<summary>` で Enter を押すと `AUTO`、Space を押すと `CUT` が実行される（`preventDefault` のため details も開かない）。
- 失敗シナリオ: キーボードで操作する管理者がショートカット一覧を開こうと Enter を押すと、意図せずプログラムが切り替わる。
- 修正案: `ACTIVATING_TAGS` に `SUMMARY` を加える。汎用的には `event.target.closest('button,a,summary,[role=button],…')` で判定し、テストを追加する。

### R3-06 [Low / 確実] トランジション中のプレビュー変更が失われる
- 実装: `TICK` の完了時に `preview: active.from` で上書きする。トランジション中の `SELECT_PREVIEW` / `SET_PIP` は受け付けるが、完了時に消える。
- 失敗シナリオ: 2秒のディゾルブ中に次のカメラ（キー 3）を選んでも、完了時にプレビューが前の画面へ戻る。そのまま Space を押すと意図しない画が出る。
- 修正案: トランジション開始後に preview が変更されたかを記録し、変更があれば完了時に preview を維持する。または、トランジション中はプレビューの選択を無効化して表示で示す。

### R3-07 [Low / 高] iOS で音量スライダーが効かない
- 実装: `video.volume = volume / 100` のみで音量を変えている。iOS Safari の `HTMLMediaElement.volume` は読み取り専用で、常に1になる。
- 失敗シナリオ: iPhone の視聴者がスライダーを動かしても音量が変わらない（F-VIEW-03）。
- 修正案: iOS ではスライダーを隠してミュートだけにするか、WebAudio の GainNode を通して音量を変える。

### R3-08 [Low / 確実] Okta ログインの失敗を表示しない
- 実装: Hub の `signInWithRedirect_failure` を処理していない。
- 失敗シナリオ: Okta 側でアプリが割り当てられていない、または PostConfirmation でエラーになると、理由が表示されないままログイン画面に戻る。
- 修正案: `signInWithRedirect_failure` を受けてエラー文言を context に保存し、LoginPage に表示する。

### R3-09 [Low / 中] カメラの切替競合で MediaStream が残る
- 実装: `openCamera` は前の await が終わるのを待たず、結果を `current.current = next` で上書きする。effect にキャンセル処理がない。
- 失敗シナリオ: getUserMedia の実行中に前面/背面を連続で押すと、先に取得したストリームが停止されずに残る。iOS ではカメラ使用表示が消えず、次の取得が NotReadableError になる場合がある。
- 修正案: effect の cleanup で取り消しフラグを立てる。取得後にそのフラグが立っていればストリームを stop して捨てる。

### R3-10 [Low / 中] 10Hz の全体再描画
- 実装: `levels`（100ms ごと）と `health`（500ms ごと）が `useSwitcher` の state で、SwitcherPage 全体（MultiView、CommentPanel 最大100件など）を再描画する。合成の drawImage も同じメインスレッドで動く。
- 失敗シナリオ: 6カメラ + スライドを合成している最中に再描画が重なり、番組映像のフレーム落ちを招く（PoC 8.2 の主要リスク）。
- 修正案: レベルメーターは独立したコンポーネントで ref を介して読む（requestAnimationFrame / interval）。重い子コンポーネントは `memo` 化する。

### R3-11 [Low / 高] 配信開始の失敗時に Composition が残る
- 実装: StartComposition の成功後に `db.update` / `db.put` が失敗すると、catch で BROADCAST 行を削除するだけで StopComposition を呼ばない。
- 失敗シナリオ: DynamoDB のスロットリングで開始 API が 500 になる。Web は送信を止めるため約60秒で自動停止するが、それまで録画と課金が続き、COMPOSITION#META がないためアーカイブにも登録されない。
- 修正案: catch で `compositionArn` があれば StopComposition を best effort で呼ぶ。

### R3-12 [Low / 確実] 合成・再生部品のテストが抜けている
- 内容: `media/compositor.ts`（drawFrame の不透明度・クリップ・黒塗り）、`audioGraph.ts`（初期ゲイン・チャンネル削除）、`videoRegistry.ts`（途絶判定）、`frameClock.ts`、`HlsPlayer` / `VideoPlayer` のテストがなく、Stryker media の mutate にも含まれない。A-01 の正しさの中核は CanvasRenderingContext2D のモックで検証できる。
- 修正案: Canvas コンテキストのモックで drawFrame の呼び出し列（globalAlpha、clip の矩形、drawImage の引数）を検証する。videoRegistry の stalled/live 判定もテストし、mutate に加える。

### R3-13 [Low / 高] 仮パスワードの期限切れから自力で戻れない
- 根拠: F-AUTH-03。仮パスワードの有効期限は7日（`delivery-stack.ts` の `tempPasswordValidity`）。
- 実装: Cognito は期限切れを `NotAuthorizedException`（Temporary password has expired…）で返す。`authErrorMessage` はこれを「メールアドレスまたはパスワードが正しくありません」と表示する。期限切れのユーザーには確認コードによる再設定も使えない。管理者が再招待しても `UsernameExistsException` で `ALREADY_EXISTS` になり、`MessageAction: 'RESEND'` による再送の経路がない。
- 失敗シナリオ: 招待から8日後にログインしようとした登壇者が、パスワード誤りだと思って何度も試し、ロックされる。管理者は再招待できず、削除してから招待し直すしか方法がない。
- 修正案: メッセージ文で期限切れを判定して「仮パスワードの有効期限が切れています。管理者に再送を依頼してください」と表示する。招待 API で既存の未確定ユーザー（`FORCE_CHANGE_PASSWORD`）には `AdminCreateUser` を `MessageAction: 'RESEND'` で呼んで再送する。

### R3-14 [Low / 確実] 配信停止の監査ログが欠落する場合がある
- 根拠: 5.3「管理者操作（配信開始停止…）をアプリログに残す」。
- 実装: `/broadcast/stop` は ended への更新 → `sendChatEvent` → `audit` の順で処理する。SendEvent が失敗すると audit に到達しない。再試行で通る ended 済みの分岐（R2-03）にも audit がない。
- 失敗シナリオ: Chat の一時障害中に配信を停止すると、DB 上は停止しているのに `broadcast.stop` の監査ログが1件も残らない。
- 修正案: DB の更新直後（SendEvent より前）に audit を出す。ended 済み分岐では `broadcast.stop.retry` のように区別して記録する。

## 追加確認（2026-10-20）で問題がなかった範囲
- IVS Chat Messaging SDK（インストール済み v1.1.1 の型定義で確認）: イベント名（`connecting`/`connect`/`disconnect`/`message`/`messageDelete`/`event`）、`DisconnectReason`（`clientDisconnect`/`serverDisconnect`/`socketError`/`fetchTokenError`）、`new SendMessageRequest(content, attributes?)`、`tokenProvider` の戻り値 `{ token }` は実装と一致する。SDK は自動で最大3回再接続し、`disconnect` はそれを諦めた後にだけ届くので、アプリ側のバックオフ再接続と重ならない。60分のセッション失効後も `tokenProvider` で再取得される。
- PasswordPage: 初回パスワード（NEW_PASSWORD_REQUIRED → confirmSignIn → /display-name）と再設定（確認コード）は仕様どおり。期限切れの仮パスワードの扱いは R3-13。
- CommentPanel / ChatProvider: `dangerouslySetInnerHTML` は使っていない。カスタムイベントで React Query を無効化する。重複した `broadcast-ended` は再取得が起きるだけで副作用はない。
- infra のセキュリティ: CloudFront の秘密鍵は `scripts/cloudfront-keypair.sh` が一時ディレクトリで生成して SSM SecureString にだけ保存する。未追跡の `infra/keys/` にあるのは公開鍵（`stg-cloudfront-public.pem`）だけで、秘密情報ではない。App Client は SRP とリフレッシュだけを許可し、`PreventUserExistenceErrors` とトークン失効を有効にしている。自己サインアップは無効。
- tests/integration（`0543849`）: R2-03 の冪等な再送（stop の再試行と recording の再試行）を、SendEvent の一時障害を注入して検証しており、実装と整合する。
