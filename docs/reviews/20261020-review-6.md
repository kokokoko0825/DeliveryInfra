### R5-01 の詳細: notify の 3 秒締め切り

- `notify`（`apps/api/src/router.ts:115-141`）は、呼び出しごとに `AbortController` を作り、3 秒後（`NOTIFY_DEADLINE_MS`、`router.ts:60`）に `TimeoutError` で abort する。
- SDK への受け渡し: `getClients().chat.send(command, { abortSignal: controller.signal })`（`router.ts:125`）。SDK v3 の `send` の第2引数（HttpHandlerOptions）は正しい渡し方で、型チェックも通る。テストも、`SendEventCommand` の呼び出しの第2引数の `abortSignal` が締め切り後に `aborted === true` になることを確かめている。
- 二重の保険: SDK が abort を無視した場合に備えて、`expired`（abort で reject する Promise）と `Promise.race` にしている。`expired.catch(() => undefined)` があるので、締め切り前に成功した場合も未処理の reject にはならない。race で負けた `send` の Promise は、race の中でハンドラーが付いているので、後から reject しても未処理にならない。
- 再試行の待ち（50→100→200ms）の途中で締め切りが来た場合: 次の試行の `Promise.race` は、すでに reject 済みの `expired` で即座に reject する。`controller.signal.aborted` が真なので、警告を出して戻る。`send` に渡す signal も abort 済みなので、HTTP の送信は始まらない。
- `finally` の `clearTimeout(deadline)` で、成功した場合にタイマーが残らない（テストの `vi.getTimerCount() === 0` で確認）。
- SDK 自身の再試行（既定3回）は 3 秒の中に収まるので、全体の上限は変わらない。
- Lambda のタイムアウトとの関係: apiFn は 29 秒（`infra/src/stacks/delivery-stack.ts:198`）。1つのリクエストで `notify` を呼ぶのは1回だけ（呼び出し元9か所: `router.ts:354`・`363`・`375`・`533`・`551`・`562`・`597`・`608`）なので、通知にかかる時間は最大約 3 秒で、29 秒に十分収まる。配信開始の例では、DB の確定 → `audit` → `notify` の順は変わっていない（`router.ts:345-354`）。締め切りを過ぎても `CHAT_EVENT_FAILED` を出して 200 を返す（`router.ts:127-131`）。

### R5-02 の詳細: WriteAttributes と keepOriginal

- Okta なし（stg）: CloudFormation の App Client は `WriteAttributes: []`（`infra/src/app-config.ts:127`、`delivery-stack.ts:244-247` で `addPropertyOverride`）。テストは `stacks.test.ts` で確認している。
- Okta あり（prod）: `updateUserPoolClient` の custom resource が `WriteAttributes: ['email']` に上書きする（`app-config.ts:135`、`delivery-stack.ts:554-569`）。`OKTA_ATTRIBUTE_MAPPING` を IdP の `AttributeMapping`（`delivery-stack.ts:550`）と共有しているので、マッピングを増やしたときに書き込み権限の付け忘れが起きない。AWS のドキュメントのとおり、IdP でマッピングした属性は App Client が書けないとフェデレーションのサインインが失敗するので、`['email']` は必須で妥当。
- `keepOriginal: { email: true }`（`delivery-stack.ts:213`）で、`UserAttributeUpdateSettings.AttributesRequireVerificationBeforeUpdate: ['email']` になる。`autoVerify: { email: true }` もあるので、前提を満たす。
- 既存の機能への影響:
  - 招待の `AdminCreateUser` は `email` と `email_verified: 'true'` を初期値として渡す（`router.ts:623`）。作成時の値なので、keepOriginal の対象外。IAM の Admin API なので、App Client の `WriteAttributes` の影響も受けない。
  - Web の初回パスワード変更は `confirmSignIn({ challengeResponse })` だけで、属性を送らない（`apps/web/src/lib/auth.ts:43`）。Web で `updateUserAttributes` を呼ぶ箇所はない（grep で確認）。`WriteAttributes: []` で壊れる画面はない。
  - 表示名は DynamoDB に保存しており、Cognito の属性ではない。
- CVSS の再評価:
  - Okta なし: `WriteAttributes: []` が効けば、利用者は自分の属性を書けない → 影響なし。
  - Okta あり: 利用者は自分のアクセストークンで `UpdateUserAttributes`（email）をまだ呼べる。ただし keepOriginal により、新しいアドレスの確認が終わるまで `email` は元の値のまま。Review-5 の 4.3 の主な根拠だった「確認前に別人のアドレスに置き換わり、管理者が取り違える」は起きない。残るのは次の2点。
    1. 新しいアドレスへの確認コードのメール送信（組織の送信元から任意のアドレスへ、本文は固定のテンプレートとコードだけ）。
    2. 本人が受信できるアドレスへの、確認済みの変更（本人の正当なアドレス変更と区別できない）。Okta のユーザーは、次のサインインでマッピングにより上書きされる。
  - 試算（CVSS 3.1）: AV:N/AC:L/PR:L/UI:R/S:U/C:N/I:L/A:N = 3.5。メールを受け取った第三者が何か操作しない限り実害はないので UI:R とした。4.0 未満で、プロジェクトの基準（0〜3.9）に収まる。
  - 「`WriteAttributes: []` を Cognito が『指定なし』として扱う」場合でも、keepOriginal があるので、上と同じ 3.5 になる（下の「未確認」を参照）。

## 未確認・要実機確認（指摘には含めない）

- **`WriteAttributes: []` を Cognito が「書き込みなし」として扱うか**: AWS のドキュメントは「指定しない場合は標準属性をすべて書ける」とだけ書いており、空の配列の扱いは明記していない。空の配列が「指定なし」と同じに扱われると、stg でも利用者が `email` の変更を要求できる。ただし keepOriginal があるので、CVSS は上の 3.5 のまま。stg で次の2点を確かめたい。
  - `aws cognito-idp describe-user-pool-client --user-pool-id <id> --client-id <id>` の結果に `WriteAttributes: []` が出るか。
  - 利用者のアクセストークンで `aws cognito-idp update-user-attributes --access-token <token> --user-attributes Name=email,Value=<別のアドレス>` が `NotAuthorizedException` になるか。
- **Okta のフェデレーションと keepOriginal の組み合わせ**: Okta 側で email が変わった利用者が次にサインインしたとき、マッピングによる email の更新が keepOriginal で保留されるかは、ドキュメントで確かめられなかった。保留されると、Cognito の email が古いまま残る（ログインはできる）。prod の Okta 連携の確認時に、Okta 側でアドレスを変えたテストユーザーでサインインして、Cognito の `email` が更新されるかを見たい。
- prod（Okta あり）のデプロイでは、CloudFormation が `WebClient` を `WriteAttributes: []` で更新してから custom resource が `['email']` を入れ直すまでの短い間、Okta のサインインが失敗しうる。OAuth の設定が一時的に消える既存の挙動と同じ種類の問題で、今回の変更で新しく生じたものではない。
