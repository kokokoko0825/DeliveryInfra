## 詳細

### R1-01 [High/確実] access token から email・ログイン方式を読んでいる
- 根拠: plan 5章 `GET /api/me` → `{userId,email,...}`、F-USR-02、5.3。AWS ドキュメント「Understanding the access token」: access token のクレームは `sub, cognito:groups, token_use, scope, auth_time, iss, exp, iat, jti, client_id, username` で、`email`・`identities` は含まれない（含めるには Essentials/Plus プランの pre token generation V2 が必要。infra は `FeaturePlan.LITE`）。
- 失敗シナリオ: どのユーザーでもログイン後に `/api/me` が `email: ""` を返す → `apps/web/src/features/auth/AuthProvider.tsx:10` で `MeResponseSchema.parse`（`z.string().email()`）が ZodError を投げる → `status='error'` → 全画面が使えない。Okta ユーザーの `loginMethod` も常に `email` になる。
- 修正案: `/api/me` では Cognito `AdminGetUser`（IAM は付与済み）または ID トークンで email と identities を取得する。もしくは cognito トリガーで DynamoDB の `LOGIN`/`PROFILE` 行に email と loginMethod を保存し、それを返す。あわせて `auth.test.ts` を実際のクレーム構造に直す（R1-12）。

### R1-02 [High/確実] スイッチャーのトークン取得が端末枠と衝突する
- 根拠: plan 5章 purpose 表 `switcher` 上限1、docs/20261019-switcher.md「配信開始時に purpose=switcher を取り直す」。
- コード: `issueStageToken` は `deviceKind: 'switcher'` があるので毎回 `storeDevice(limit=1)` を実行する（router.ts:128,132）。Web は `switcherToken(stage)` のたびに新しく `requestStageTokens('switcher')` を呼び（useSwitcher.ts:29）、`start()` では production と slide を並列に開始する（:161-166）。`deviceId` は捨てているのでハートビートも DELETE もしない。
- 失敗シナリオ: 起動直後、production は枠を取れるが slide は 409 → バックオフで約45秒後に回復。その後45秒以内に「配信開始」を押すと broadcast も 409 → `startPublishing` が例外になり配信できない。production/slide の再接続も、45秒以内に別のトークン取得があると連鎖して失敗する。
- 修正案: (a) switcher は端末枠を使わない（API は admin ロールの検証のみ）。上限1を守りたいなら (b) 1回の応答で返る3本のトークンを Web 側で使い回し、再接続時は deviceId を DELETE してから取り直し、ハートビートも送る。KISS の観点では (a) を推奨する。

### R1-03 [High/確実] Composition 自動終了後に配信状態が `live` のまま固まる
- 根拠: F-SW-09、F-REC-01/02。AWS StartComposition の説明: 「全参加者の切断から1分のタイムアウトで Composition は停止し、リソースは削除される」。
- 失敗シナリオ: 視聴者が0人の検証配信中に管理者 PC のブラウザがクラッシュし、1分以上復帰できない → Composition が終了し、recording Lambda はアーカイブを作るが `BROADCAST/CURRENT` は `live` のまま → 「配信終了」を押すと `StopComposition`(ResourceNotFound) で 500 → `ended` に更新されず、`broadcast-ended` も送られない → `POST /broadcast/start` は条件 `#status = :ended` を満たさないので 409 が続き、DynamoDB を手で直すまで配信できない。`Session Failure` イベントも未処理。
- 修正案: stop では `ResourceNotFoundException` を無視して `ended` に進める。recording Lambda で `Session End`/`Session Failure` を受けたとき、`BROADCAST/CURRENT.compositionArn` が一致していれば `ended` にして `broadcast-ended` を送る。

### R1-04 [Medium/確実] コメント表示名のなりすまし
- 根拠: 5.3「入力値の検証」、F-NAME-03、plan 5章 Chat「メッセージ属性 {displayName}」。
- コード: chat-review.ts:57 は `event.Attributes`（クライアントが自由に指定できる）をそのまま `ALLOW` 応答に入れる。Web の `toComment` は `message.attributes?.displayName` を `sender.attributes`（サーバーがトークンに入れた値）より優先する（chat.ts:16）。
- 失敗シナリオ: 視聴者が IVS Chat SDK で `SendMessageRequest('...', { displayName: '運営事務局' })` を送ると、ライブ表示では「運営事務局」と出る（DynamoDB の履歴は正しい名前なので、再読込すると名前が変わる）。長さ制限も効かない。CVSS 3.1 の目安は AV:N/AC:L/PR:L/UI:R/S:U/C:N/I:L/A:N。
- 修正案: 審査 Lambda で `Attributes: { displayName: profileItem.displayName }` に上書きして返す。Web は `sender.attributes.displayName` を優先するか、メッセージ属性を使わない。

### R1-05 [Medium/確実] スライドを iframe で表示できない
- 根拠: F-SLD-03「ブラウザ内で閲覧」。
- コード: viewer-response 関数が `/files/*` にも `x-frame-options: DENY` と CSP `frame-ancestors 'none'` を付ける。SlidesPage は同一オリジンの `/files/slides/<id>.pdf` を iframe で埋め込む。
- 失敗シナリオ: U-02 で「閲覧」を押すとダイアログ内が空白、またはブラウザのブロック表示になる（新しいタブのリンクだけは動く）。
- 修正案: `/files/*` 用に別のヘッダー関数を用意し、`X-Frame-Options: SAMEORIGIN` と `frame-ancestors 'self'` を付ける（free プランでも CloudFront Functions は使える）。

### R1-06 [Medium/確実] `/api/status` が常に「ステージなし」を返す
- 根拠: F-OPS-02、5.3 IAM 最小権限。
- コード: `ListStageSessionsCommand` を `Promise.all` で呼ぶが、API ロールに `ivs:ListStageSessions` が無い → AccessDenied → catch で `{exists:false}`。
- 修正案: `ivs:ListStageSessions` を stageArns に付与する。あわせて、権限エラーを「存在しない」として握りつぶさず、エラー内容をログに出す。

### R1-07 [Medium/確実] 台数上限が IVS 接続と連動しない
- 根拠: F-CAM-06「7台目は接続を拒否」、F-MIC-05、plan 3章（15秒ハートビート・45秒失効）。
- 失敗シナリオ: CAM3 の Wi-Fi が API にだけ一時的に届かない（WebRTC は別経路で生きている）状態が45秒続く → 枠が失効して7台目の CAM7 が取得できる → production ステージに7台が同時に送信する。また 409 を受けたクライアントでも、取得済みトークン（有効期限10分）の再利用や重複発行で接続できる。
- 修正案: 枠の失効時（ハートビート 404 を返す時や DELETE 時）に `DisconnectParticipant` で該当 participantId を切断する。または、トークン発行時に `ListParticipants`（PUBLISHED）で実数を数えて二重にチェックする。少なくとも participantId を枠レコードに保存する。

### R1-08 [Medium/確実] 非公開アーカイブを Cookie で再生できる
- 根拠: F-REC-03「公開停止」、plan 3章「管理者が公開操作」、5.3。
- 失敗シナリオ: 公開中に視聴した利用者が `playbackPath`（例 `/files/archives/<stageId>/<sessionId>/.../media/hls/multivariant.m3u8`）を控えておけば、公開停止後もログインして Cookie を取り直すだけで再生できる。録画直後の非公開状態でも、URL を推測・共有されれば同じ。
- 修正案: アーカイブ用には Cookie の Resource を公開中アーカイブのプレフィックスだけに絞って発行する（`POST /api/archives/{id}/cookies` を新設し、`published` か admin のときだけ発行する）。

### R1-09 [Medium/確実] 降格が即時に効かない
- 根拠: 5.3 サーバー側ロール検証、2章。
- 失敗シナリオ: admin を viewer に変更しても、本人の access token の `cognito:groups=['admin']` は最大1時間有効 → その間 `/api/users/*` などを操作し続けられる。
- 修正案: ロール変更時にも `AdminUserGlobalSignOut` を呼ぶ。加えて、管理系 API では `AdminListGroupsForUser` で現在のグループを再確認する（呼び出し回数が少ないので負担は小さい）。

### R1-10 [Medium/確実] 全件 Scan への依存
- 根拠: 5.1 コメント1秒以内、docs/20261019-api-design.md「GSI は使わない…Scan」、9章コスト。
- 失敗シナリオ: 1年間で数万件のコメントが溜まると、コメント1件ごとに審査 Lambda が強整合 Scan でテーブル全体を読む（RCU 課金とレイテンシーが増える。3秒タイムアウトで fallback DENY になりうる）。11台の端末が15秒ごとに `deviceId` でフル Scan する。300人の同時入室で `/comments/recent` が300回フル Scan する。
- 修正案: NG ワードは `PK=NGWORD, SK=<word>` の Query にし、Lambda 内で短期キャッシュする。端末は `PK=DEVICE, SK=<purpose>#<slot>` にし、deviceId からスロットを引ける形（deviceId にスロットを埋め込むなど）にする。コメントは `PK=COMMENT, SK=<sentAt>#<id>` で降順に Query し `Limit 100` にする。

### R1-11 [Medium/確実] 一括招待の部分失敗
- 根拠: F-USR-01（CSV 一括）。
- 失敗シナリオ: 50件中10件目が既存ユーザー（`UsernameExistsException`）→ 500 `INTERNAL_ERROR`。9件は作成済みでメールも送られているのに画面にはエラーしか出ない。再実行すると1件目で止まる。
- 修正案: 1件ずつ try/catch して `{ invited, failed:[{email, reason}] }` を返す。既存ユーザーはスキップ扱いにする。

### R1-12 [Medium/確実] モックが実際のトークン構造と違う
- 根拠: plan 8章（意味のあるテスト）。
- 内容: `auth.test.ts` は `verify` の戻り値に `email`・`identities` を入れているが、実際の access token には無い。`router.test.ts` は `authenticate` 自体を差し替えて email を固定している。このため R1-01 がテストで検出されない。
- 修正案: Cognito access token と同じ形のフィクスチャ（`sub, cognito:groups, username, client_id, token_use`）を使い、`/api/me` の応答を `MeResponseSchema.parse` で検証する契約テストを追加する（Wave2 の結合テストで扱うのが適切）。

### R1-13 [Medium/可能性あり] WAF のレート制限
- 根拠: 5.3（IP ごとのレート制限）、前提「最大数百人」。
- 失敗シナリオ: 社内の視聴者300人が同じ出口 IP で配信開始時に一斉にアクセスする。1人あたり SPA アセット約20件 + config/me/broadcast/tokens/comments/cookies などで約30件 → 5分で約9,000件となり 2,000 を超えてブロックされる。
- 修正案: `/api/*` だけを対象にする scope-down statement を付けるか、上限を 10,000 程度に上げ、`-c` で環境ごとに設定できるようにする。

### R1-14〜R1-25 [Low]
- R1-14: `db.update(..., 'attribute_exists(PK)')` の例外がそのまま 500 になる。`ConditionalCheckFailedException` を 404 にまとめて変換する。
- R1-15: CSV の列に `messageId`・`deleted` を追加する。`csvCell` の判定を `/^[=+\-@\t\r]/` に広げる（OWASP の CSV injection 対策）。
- R1-16: shared の `CommentSchema` に `.trim()` と制御文字の refine を入れ、Web と API で同じ検証を共有する（DRY）。審査 Lambda は trim 後の Content を返す。
- R1-17: `fetchToken` 内で `await releaseDevice(prev)` してから再要求する。
- R1-18: `storeDevice` で、同じ purpose かつ同じ `deviceName` の有効な枠があれば 409 `DEVICE_NAME_IN_USE` を返す（ただし同一ユーザーの再接続は除く）。
- R1-19: `userId === principal.userId` の自己操作をサーバーで 400 にする。
- R1-20: PostConfirmation（外部 IdP）でも `LOGIN` 行を書く。
- R1-21: recording 関数に `ivs:GetComposition`（composition/*）を付与する。
- R1-22: ライフサイクルの一律削除をやめ、アーカイブ行に `expiresAt` を持たせて削除処理を行うか、仕様側の「延長可」を見直す。
- R1-23: `CognitoJwtVerifier.create` をモジュール読み込み時に1回だけ生成し、使い回す。
- R1-24: ユーザー一覧は `ListUsersInGroup` × 5 でロールを引き、DynamoDB は `BatchGet` にする。

## 指摘しなかった項目（確認済みで問題なし）
- 秘密情報のハードコード: なし（署名鍵は SSM SecureString、Okta secret も SSM）。`keys.ts` は破棄済み鍵の公開鍵のみ。
- OAC: 関数URL は `AWS_IAM`、S3 は全バケット BLOCK_ALL + OAC。迂回経路は見当たらない。
- presigned POST: `content-length-range 1..50MB`・`Content-Type` 固定・キーはサーバー側で生成。complete で HEAD のサイズ一致と `%PDF-` を検証している。
- XSS: `dangerouslySetInnerHTML`/`innerHTML` の使用なし。CSP は `script-src 'self'`。
- 署名付きCookie: 有効期限1時間、`Path=/files/; Secure; HttpOnly; SameSite=Lax`、host は `^[a-z0-9]+\.cloudfront\.net$` に限定。範囲の問題は R1-08 のみ。
