## 詳細

### R4-01 [Low / 高] SendEvent の失敗で、確定済みの操作が 500 になる
- 根拠: 5.3（管理者操作のログ）、F-SW-09。R3-14 と同じ原因で、停止以外の操作にも及ぶ。
- 実装: 配信開始は、DB を live に更新して Composition を開始した後に `sendChatEvent('broadcast-started')` を呼ぶ（`router.ts:327`）。ここで失敗すると例外が `failureResponse` に流れて 500 になり、`audit` も実行されない。スライドの complete/order/delete（504/522/533）とアーカイブの patch/delete（568/579）も、DB・S3 を変更した後に SendEvent を呼ぶので同じ構造になる。
- 失敗シナリオ:
  - 例1: Chat の一時障害中に配信を開始する。API は 500 を返すが、DB は live で、録画も始まっている。Web は `start()` の catch で `stopPublishing()` を呼び、「処理に失敗しました」と表示する。`refresh` で live になるため、R3-04 の再開経路で番組送信は戻る。しかし数秒間、番組が途切れる。視聴者には `broadcast-started` が届かず、最大60秒（`WatchPage` のポーリング）待機画面のまま。`broadcast.start` の監査ログも残らない。
  - 例2: スライドの削除で SendEvent が失敗する。管理者が再試行すると、行は消えているので 404「対象が見つかりません」になる。
- 修正案: 共通の `notify(eventName)` を作り、SendEvent を best effort にする（失敗は `console.error` で記録し、応答は 200）。`audit` は DB の確定直後、SendEvent より前に出す。クライアントには 60 秒ポーリングと再取得の手段があるので、通知の欠落は自然に回復する。R3-14 もこれで解消する。

### R4-02 [Low / 高] コメント停止の解除が本人に反映されない
- 根拠: F-CMT-05。
- 実装: 停止するときは `DisconnectUser` を呼ぶ。そのため本人のクライアントは `serverDisconnect` → `refresh()`（`/me` の再取得）→ 再接続（トークン再発行）と進み、送信欄が無効になる。一方、解除のときは DB を更新するだけで、本人には何も届かない（`router.ts:450` は `if (suspended)` のときだけ切断する）。本人の画面は `me.commentSuspended === true` のまま `sendBlockReason` が `'suspended'` を返し続ける。チャットのトークンにも `SEND_MESSAGE` がない。
- 失敗シナリオ: 管理者が誤って停止したユーザーを、コメント管理画面ですぐに解除する。本人には「管理者によりコメント送信が停止されています」が出たままになり、再読み込みするまで送信できない。
- 修正案: 解除のときも `DisconnectUser`（reason: 'コメント送信停止の解除'）を呼ぶ。既存の `serverDisconnect` → `refresh()` → 再接続の経路で、`/me` とトークンの権限が両方更新される。統合テストの `world.chat.disconnected` で検証できる。

### R4-03 [Low / 高] 審査 Lambda の DENY 理由が表示されない
- 根拠: F-CMT-02/05。IVS Chat の公式ドキュメント（Message Review Handler）によると、`ReviewResult: DENY` で `Attributes.Reason` を返した場合、送信者は理由をエラーメッセージに含む WebSocket 406 を受け取る。SDK v1.1.1 の型では、`ChatError` は `errorCode` と `errorMessage` を持つ。
- 実装: `chatErrorMessage` は 406 をすべて「NGワードを含むか、送信できない内容です」に置き換えるため、`errorMessage` に入っている審査 Lambda の理由（「コメントは3秒に1回まで送信できます」「コメントの送信が停止されています」「表示名を設定してください」）を捨てている。
- 失敗シナリオ: 視聴者がスマホと PC で同時に開いていて、両方から3秒以内に送る。または再読み込み直後（クライアント側の `lastSentAt` が消えた状態）に送る。サーバーの3秒制限で DENY されるが、「NGワードを含む」と表示されるので、本文を書き換えて何度も試す。
- 修正案: 406 のときは `errorMessage` に理由があればそれを表示し、なければ現行の文言にする。理由の文言は審査 Lambda 側で日本語に固定済み（200文字に切り詰め、Attributes の上限 1KB 以内）。

### R4-04 [Low / 高] 初回パスワード設定のセッション切れの表示が誤っている
- 根拠: F-AUTH-03。App Client は `AuthSessionValidity` を指定していないので、Cognito の既定値の3分になる（`infra/src/app-config.ts` の `buildWebClientSettings`）。
- 実装: 3分を過ぎてから `confirmSignIn` を呼ぶと、Cognito は `NotAuthorizedException`（Invalid session for the user, session is expired.）を返す。`authErrorMessage` はこれを「メールアドレスまたはパスワードが正しくありません」と表示する。しかしこの画面にはメールアドレスの入力欄がなく、ログインに戻る必要があることも示さない。
- 失敗シナリオ: 招待された登壇者が、パスワードの条件（12文字・大小英字・数字）を考えているうちに3分を過ぎる。送信するとパスワードが誤っていると表示され、何度入力し直しても通らない。
- 修正案: `NewPasswordForm` で `NotAuthorizedException` かつ message が `/session is expired|Invalid session/i` に一致したら、「時間が経過したため、もう一度ログインからやり直してください」と表示し、`/login` へのボタンを出す。あわせて `AuthSessionValidity` を 10〜15 分に延ばすことも検討する（上限は 15 分）。

### R4-05 [Low / 中] ネイティブ HLS の復旧が際限なく繰り返されるおそれ
- 根拠: R3-03 の「3回連続で進まなければエラー表示」。
- 実装: ネイティブの経路は、video の `error` を種類にかかわらず `recover` に回す（42行）。再試行の回数は `playing` で0に戻る（52行）。復旧のたびに同じ位置へシークして再生するので、そこで `playing` が発火してから同じエラーになると、回数は永久に3に達しない。毎回 `POST /api/archives/{id}/cookies` と再読み込みが走る。hls.js の経路はネットワークエラーだけを対象にしているので問題ない。
- 失敗シナリオ: Safari（iPhone）で、録画の途中に壊れたセグメントがある（`MEDIA_ERR_DECODE`）。その位置で、エラー → Cookie 再取得 → 再読み込み → 再生開始 → エラーを繰り返し、画面がちらつき続けて API 呼び出しも増え続ける。
- 修正案: `video.error?.code === MediaError.MEDIA_ERR_NETWORK`（必要なら `MEDIA_ERR_SRC_NOT_SUPPORTED` も。Safari は 403 の playlist をこちらで返す場合がある）のときだけ復旧する。回数を0に戻す条件は、`playing` ではなく「復旧前の位置より `timeupdate` が進んだこと」にする。

### R4-06 [Low / 高] Dialog/Sheet/Sidebar の英語文言と小さい閉じるボタン
- 根拠: plan 6章（日本語のみ、Apple HIG の 44pt 以上のタップ領域）、5.6（キーボード操作・アクセシビリティ）。
- 実装: shadcn の生成コードのままで、`DialogContent`/`SheetContent` の閉じるボタンは `sr-only` の文言が「Close」、アイコンは `size-4` で余白もない。`SlidesPage`（スマホで PDF を見るダイアログ）、`RetainUntilDialog`、`TitleEditDialog` は既定の `showCloseButton` のまま使っている。モバイルのサイドバー（Sheet）の見出しは「Sidebar」「Displays the mobile sidebar.」。`AppLayout` の `SidebarTrigger` には日本語の `aria-label` を付けているが、これらは漏れている。
- 失敗シナリオ: iPhone の VoiceOver 利用者がスライドを開くと「Close, button」と読み上げられる。メニューを開くと「Sidebar, Displays the mobile sidebar.」と読まれる。晴眼の利用者も、PDF ダイアログの右上の 16px の × を押しにくい。
- 修正案: `dialog.tsx`/`sheet.tsx` の sr-only を「閉じる」にし、ボタンに `size-11 grid place-items-center` を付ける。`sidebar.tsx` の見出しを「メインメニュー」と「ページを移動します」にする。

### R4-07 [Low / 高] API Lambda の未使用の IAM 権限
- 根拠: 5.3「IAM は最小権限」。
- 実装:
  - `apiFn` に `ivs:GetComposition`（375行）と `ivs:ListCompositions`（Resource `*`、377行）があるが、`apps/api/src/router.ts` はどちらも呼ばない。`GetComposition` を使うのは recordingFn で、そちらには別に付与済み。
  - `apiFn` に `s3:PutObject/GetObject/DeleteObject` を `comment-exports/*` に対して付けている（384-389行）。しかし CSV エクスポートは応答の本文で直接返すので（`router.ts:454-458`）、S3 は使わない。
  - `chatReviewFn` は `table.grantReadWriteData`（334行）だが、実際に使うのは GetItem・Query・PutItem・TransactWriteItems（Put）だけ。
- 失敗シナリオ: API Lambda の認証情報が漏れたり、SSRF などで悪用されたりした場合に、アカウント内の全 Composition を列挙できる。
- 修正案: 上の3つを削除する。chatReviewFn は `grantReadData` ＋ `dynamodb:PutItem` に絞る（TransactWrite の Put は PutItem 権限で足りる）。`infra/test/stacks.test.ts` で、apiFn のポリシーに `ivs:ListCompositions` が含まれないことを検証する。

  - 色の直書きは shadcn の生成コード（`bg-black/50` のオーバーレイ、`destructive` の `text-white`、スライダーのつまみの `bg-white`）だけで、アプリのコードにはない。
  - 送信・スイッチャー・コメントのボタンは `h-11`/`size-11`。
  - ショートカットは R3-05 の修正で、フォーカス中の部品の操作と衝突しない。

## 未確認・要実機確認（指摘には含めない）

- スライドの PDF 応答に付く CSP の `object-src 'none'` が、Chrome の内蔵 PDF ビューアー（iframe 内）の表示を妨げないか。仕様上は関係しない見込みだが、stg の実機で `/slides` のダイアログを開いて確認したい。
- `/files/*` ビヘイビアはアプリから使われていない（スライドとアーカイブは個別のビヘイビアで処理される）。署名ポリシーがパスを限定しているので悪用はできないが、YAGNI の観点では削除できる。削除すると、content バケットの `AWSLogs/`（チャットログ）が CloudFront 経由で取得されうる経路も構造的になくなる。
