### 見送られた chatReviewFn の権限縮小の評価

判断: **見送りは妥当**。ただし、Fix-4 に書かれた理由（統合テストがバンドル済みの `Database` クラスの参照を権限として検出する）はテストの都合で、本質的な理由ではない。記録しておくべき理由は次の2点。

- R4-07 の案（`grantReadData` ＋ `dynamodb:PutItem`）にしても、守れる範囲はほとんど増えない。単一テーブルなので、PutItem だけでも任意の行を上書きできる。例: `ARCHIVE` 行を過去の `ttl` で上書きする → TTL で削除される → archive-expiry が録画を消す。`USER#<id>/PROFILE` や `BROADCAST/CURRENT` も上書きできる。本当に絞るなら `dynamodb:LeadingKeys` の条件（`USER#*`・`COMMENT`・`COMMENT#*`・`NGWORD`）が要る。それでも `USER#<id>/PROFILE`（停止フラグ）は守れない。
- 攻撃面が小さい。chatReviewFn の入力はコメント本文と送信者 ID だけで、zod の検証と文字列の比較にしか使わない。コードが実行される経路はない。

したがって、R4-07 の見送りによって CVSS 4.0 以上になる経路はない。

## 詳細

### R5-01 [Low / 中] `notify()` に全体の時間上限がない
- 根拠: plan 5章（SendEvent は内部で再試行し、失敗しても成功応答を返す）、R4-01。
- 実装: `notify` は SendEvent を最大4回呼ぶ（初回と3回の再試行。`router.ts:115-126`）。一方 `IvschatClient` は既定の設定で作られている（`aws.ts:13`）。そのため、SDK 自身の再試行（既定で3回まで）が各回に重なり、最大12回の呼び出しになる。リクエストのタイムアウトも指定していない。API Lambda のタイムアウトは 29 秒（`delivery-stack.ts:197`）。
- 失敗シナリオ: IVS Chat の API がエラーを返さずに応答しなくなった状態で、管理者が配信を開始する。DB は live、Composition も開始済み、`broadcast.start` の監査ログも出た後に、`notify` が 29 秒待って Lambda がタイムアウトする。CloudFront は 5xx を返す。Web は `startBroadcast` の例外で `started = false` のまま `stopPublishing()` を呼び（`BroadcastPanel.tsx:84`）、「処理に失敗しました」と表示する。これは R4-01 の例1と同じ状態で、番組の送信が一度止まる（`refresh` で live を読み、R3-04 の再開で戻る）。また、30秒近くボタンが busy のままになる。
- 修正案: `notify` 専用の Chat クライアントを作り、`maxAttempts: 1` と `requestHandler: { requestTimeout: 1000, connectionTimeout: 1000 }` を指定する。再試行は `notify` の3回だけにして、全体を約 5 秒以内に収める。あるいは、`notify` の全体に締め切り（例: 3 秒）を設け、超えたら `CHAT_EVENT_FAILED` で戻す。テストは、SendEvent が解決しない Promise を返すモックで、応答が 200 になることを確かめる。

### R5-02 [Low / 中] 利用者が自分のメールアドレスを書き換えられる
- 根拠: 5.3（招待したユーザーだけ、最小権限）、F-AUTH-02、F-USR-02。
- 実装: App Client の設定（`app-config.ts:113-123`）に `WriteAttributes` も `ReadAttributes` もない。Cognito の仕様では、`WriteAttributes` を指定しない App Client は、書き込み可能な標準属性をすべて書ける。`email` は `mutable: true`（`delivery-stack.ts:210`）で、`keepOriginal`（`AttributesRequireVerificationBeforeUpdate`）も指定していない。SRP で得たアクセストークンには `aws.cognito.signin.user.admin` のスコープが付く。このため、利用者は Cognito の `UpdateUserAttributes` をアクセストークンで直接呼べる。
- 失敗シナリオ: 招待された viewer が、ブラウザの開発者ツールでアクセストークンを取り出し、`UpdateUserAttributes` で `email` を `ceo@example.co.jp`（プールに未登録のアドレス）に変える。`keepOriginal` がないので、検証の前に値が置き換わる（`email_verified` は false になる）。A-05 のユーザー一覧（`router.ts:763`）と A-04 の停止中ユーザー一覧（`CommentsAdminPage.tsx:44`）には、管理者から見ると別人のアドレスが表示される。管理者がこの表示を頼りにロールや停止を判断すると、相手を取り違える。また Cognito は、新しいアドレスに確認コードのメールを送る。これを繰り返すと、組織の送信元（SES を設定した場合は組織のドメイン）から任意のアドレスにメールを送らせることができる。
- CVSS 3.1 の試算: AV:N/AC:L/PR:L/UI:N/S:U/C:N/I:L/A:N = 4.3。データの漏えいはなく、影響は本人の行の表示に限られる。プロジェクトの基準では Low だが、CVSS の数値は 4.0 を超えうる。
- 修正案: UserPool に `keepOriginal: { email: true }` を指定する。これで、新しいアドレスの確認が終わるまでは元のアドレスのままになる。Okta 連携では、マッピングした属性に App Client の書き込み権限が要る。そのため `WriteAttributes` から `email` を外すと、連携ログインが壊れるおそれがある。`keepOriginal` の方が安全。あわせて、A-05 の一覧にはメールアドレスだけでなく `userId` も出すと、取り違えに気づきやすい。stg で、`aws cognito-idp update-user-attributes --access-token ...` が成功するかを確認すること。

### R5-03 [Low / 高] apiFn に録画バケットの未使用の `s3:GetObject` が残っている
- 根拠: 5.3「IAM は最小権限」、R4-07。
- 実装: `delivery-stack.ts:389-391` で、apiFn に `recordingBucket.arnForObjects('*')` への `s3:GetObject` と `s3:DeleteObject` を付けている。しかし API が録画バケットに使うのは、`deletePrefix` の `ListObjectsV2` と `DeleteObjects` だけ（`apps/api/src/storage.ts:10`・`13`、`router.ts:594`）。`GetObjectCommand` は slides の先頭5バイトを読む1か所だけ（`router.ts:516`）で、その権限は `slides/*` の文で足りている。
- 失敗シナリオ: API Lambda の認証情報が漏れた場合に、非公開のアーカイブを含む全録画をダウンロードできる。ただし API Lambda は CloudFront の署名鍵（SSM）も読めるので、増える影響は小さい。
- 修正案: `s3:GetObject` を外し、`s3:DeleteObject` だけにする。`infra/test/stacks.test.ts` で、apiFn のポリシーに録画バケットへの `s3:GetObject` がないことを検証する。

### R5-04 [Low / 高] 閉じるボタンの拡大で、長いダイアログタイトルが隠れる
- 根拠: plan 6章（Apple HIG）、R4-06。
- 実装: 閉じるボタンを `absolute top-2 right-2 size-11` にした（`dialog.tsx:73`）。ボタンは、ダイアログの上端と右端から 8〜52px の範囲を覆う。一方、`DialogContent` の余白は `p-6`（24px）で、`DialogHeader` には右の余白がない。そのため、タイトルの1行目の右端の約 28px がボタンと重なる（修正前の 16px のアイコンでは、重なりは約 8px だった）。`SlidesPage` はタイトルにスライド名（最大100文字、`index.ts` の `SLIDE_TITLE_MAX`）をそのまま出す（`SlidesPage.tsx:21`）。スマホでは中央揃え（`text-center sm:text-left`）なので、長い名前は1行目が端まで伸びる。
- 失敗シナリオ: 「2026年度 第3四半期 事業報告と来期の重点施策について（最終版）」のような名前のスライドを iPhone で開くと、1行目の末尾の2〜3文字が × ボタンの下に隠れる。
- 修正案: `DialogContent` で `showCloseButton` のとき、`DialogHeader` に `pr-12` を付ける（例: `has-data-[slot=dialog-close]:[&_[data-slot=dialog-header]]:pr-12`）。または `SlidesPage` の `DialogHeader` に `className="pr-12"` を付ける。`RetainUntilDialog`・`TitleEditDialog` は見出しが短い固定文なので、影響はない。
