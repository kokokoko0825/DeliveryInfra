# 会場音声 多台数 PoC 実装・検証計画

## 実装状況（2026-10-21）

- 最大3マイク・5スピーカーの直接WebRTC接続、PCM DataChannel方式と音声トラック方式の選択、ルーム単位のシグナリングを実装した。
- `/send/mic` では配信用に取得済みの同一 `MediaStream` を会場音声にも渡すスイッチを追加した。会場用PoCページでは独立したマイク入力を取得する。
- PoC画面に接続状態、毎秒ヘルス記録、IndexedDBへの端末内保存、CSV/JSON出力、明示操作による音響録音と録音ファイルのダウンロードを追加した。
- 現段階で機械的に確認したのは接続ロジック、ログ処理、録音UI/ヘルパーである。実機での接続可否、入力から出力までの音響遅延、音質、iOSバックグラウンド挙動は未確認。RTTは音響遅延の代替指標ではない。
- 初回PoCではWebCodecs Opus比較と録音波形からの遅延自動算出を実装対象から外した。録音はブラウザ対応形式（WebM/OpusまたはMP4）で端末に保存し、分析は別途行う。実機検証後に必要性を判断する。
- CI相当の確認結果：テスト、型チェック、lintは成功。詳細と残作業は `docs/20261021-venue-audio-poc-implementation.md` に記録する。

## 意図

このPoCの目的は通信状態の計測ではなく、仕様書にある「複数マイクの音声を会場内LANで複数スピーカー端末へほぼリアルタイムに届けられるか」を実機で判断できる形にすること。システム上は最大3マイク・5スピーカーの接続枠を用意するが、実機検証で3対5や1対5を必須条件にしない。手持ち端末で可能な1対多・多対多を中心に、1対1、1対3、2対2、3対1などを検証する。各試験の合否を後続試験の開始条件にはしない。

## 根拠と仕様の優先順位

- `docs/spec/requirements.md` の F-VEN-01〜12 と 8.2 を基準にする。
- F-VEN-06 の目標は入力からスピーカー出力まで50 ms以下、上限は60 ms。
- F-VEN-02/03 の候補を比較する。初回PoCではDataChannel + PCMとWebRTC音声トラックを比較する。WebCodecs Opusは初回実装に含めず、二方式の実機結果を見て必要なら追加する。
- F-VEN-05 の通り、音声は同じWi-Fi/テザリング内で端末間を直接接続し、クラウド中継・STUN/TURN・新規AWSリソースを使わない。シグナリングだけ既存stg APIを使う。
- 現行仕様 F-VEN-08 の「最大3マイク」は維持し、今回の依頼による「最大5スピーカー」を上書き仕様として扱う（仕様書の現行値は1〜2台）。
- ユーザー確認済み：マイク3台の音声は全スピーカーで同時再生する。スピーカー側で各音声を合成する。手動ミキサーは追加せず、端末の音量ボタンで音量を調整する。
- 実機環境確認済み：iPhone 2台、iPad 1台、MacBook 1台。iPhone/iPadにはChromeがある。iOS版Chrome/SafariはいずれもWebKit系なので、Android Chromeの実機検証とは区別する。Android端末はない。
- 実機数は最大4台。実機検証は1対1、1対3、2対2、3対1など、複数端末でのfan-outとfan-inを確認できる構成を主対象とする。1対5や3対5はユーザーの実機確認要件ではなく、追加端末がない限り実機音響の合否対象にしない。必要なら合成クライアントで接続枠・シグナリング負荷のみを補助確認し、実機音響結果と混同しない。外部録音機材は使わず、手持ちのiPhone 2台・iPad 1台・MacBookをマイク/スピーカー/録音役に割り振る。役割の組合せごとに実行可能な音響測定方法を選び、録音役を別に確保できない構成では音響遅延を未測定として明示する。

## 現状と主な差分

- 現行PoCはマイク1台・スピーカー1台の固定シグナリング枠で、複数端末の同時参加や同じマイクからの多重接続に対応しない。
- 音声は10 msごとのPCM16フレームとして送るが、受信側には仕様の5〜15 msを明示制御するジッタバッファがない。
- RTTのCSVはネットワークping/pongの記録であり、音響的な入力〜出力遅延の合否には使わない。残す場合も補助メトリクスとして区別する。
- `CLAUDE.md` と `AGENTS.md` はこのワークツリーおよび確認した親階層では見つからなかった。既存制約は `docs/spec/requirements.md` と実装/CI設定から確認する。Claude Codeは使わず、委譲する場合はCodex workerのみを使う。

## 方針と選択理由

1. **端末間メッシュ接続**：各マイクから各スピーカーへ直接WebRTC接続する。最大構成は3×5の15本の一方向音声経路。サーバーが音声を中継せず、「中継役なし」の仕様を守れる。各スピーカーのAudioWorkletで最大3ストリームを加算し、ピーク制御でクリッピングを避ける。
2. **ルームとスロットを導入**：短いPoCルームIDの中にMIC1〜MIC3、SPK1〜SPK5を登録する。既存API/DynamoDBに短命の参加・offer/answer状態を置き、参加者一覧は既存APIをポーリングして把握する。上限超過・期限切れ・所有者以外の削除をAPI側で拒否する。
3. **音声方式を選択可能にする**：初回PoCでDataChannel+PCMとWebRTC音声トラックを切り替えられる。WebCodecs Opusは初回実装に含めず、実機結果を踏まえた次段階の候補とする。
4. **音響遅延と通信診断を別データにする**：DataChannelのRTT、受信順序/欠落/バッファ状態、AudioWorkletのunderflow/overflowを端末内IndexedDBへ保存しCSV/JSONで出力する。これらを入力〜スピーカー出力遅延の代用にしない。録音は明示操作でブラウザ対応形式のファイルとして端末へダウンロードし、初回PoCでは遅延の波形自動算出を行わない。測定値の算出は録音ファイルと測定条件を確認して別途行う。
5. **再現可能な一括テスト**：検証ページから任意の参加構成（最大3マイク・5スピーカー）を設定できる。実機の標準ケースとして1対1、1対3、2対2、3対1を案内し、方式・参加スロット・ランID・ヘルス情報を記録してCSV/JSON manifestを出力する。録音ファイルはログとは別に端末へダウンロードする。
6. **既存PoCを壊さず移行可能にする**：既存の `/send/mic` の同一MediaStreamをIVSと会場音声へ分岐する要件を維持する。既存配信経路には触る範囲を限定し、回帰テストでIVS単独・併用時の動作を保護する。

## 実装作業

### A. API・シグナリング

- ルーム作成/参加/退出、役割とスロット予約、参加者一覧、peerごとのSDP交換を追加する。
- 最大3マイク・5スピーカー、ルーム分離、TTL、所有権、同時予約競合、参加者消失をテストする。
- 新AWSリソースなしで既存APIとテーブルを再利用する。

### B. 音声経路

- 各マイクは最大5peerへfan-outし、各スピーカーは最大3peerから受信する。
- PCM DataChannelにシーケンス番号、欠落/並べ替え処理、設定可能な5〜15 msジッタバッファ、キュー上限を実装する。
- PCM方式と音声トラック方式を切替可能にする。WebCodecs Opusは初回PoCの対象外。
- 3入力の再生ミックス、ピークリミッター、ローカルミュートを実装し、音量調整UIは追加しない。
- 接続状態、参加者、方式、音声ドロップ/underflowを画面に表示する。

### C. 計測・出力

- ラン単位で条件・端末/ブラウザ情報・開始終了・参加スロットを保存する。
- peer単位の送受信フレーム、欠落、late/out-of-order、DataChannel統計、AudioWorkletキュー/underflow、方式別設定をraw CSVに記録する。
- CSVの列定義とバージョンを固定し、時刻基準（端末単調時計/UTC）を混同しない。
- ブラウザ対応形式の音響録音を端末へダウンロードする。初回PoCでは録音波形の自動解析や50 ms/60 ms超過集計は行わない。
- エクスポート後に保存済みrawデータと突合できるrun IDを付け、同じランを再出力してもデータを二重カウントしない。

### D. 実機テスト画面と手順

- 参加した実端末の数と構成を表示し、最大3マイク・5スピーカーの範囲で任意に構成できる。
- 1対1、1対3、2対2、3対1を手持ち4台で行う標準ケースとして案内する。端末の役割入替えも記録する。
- F-VEN-06に従い、基準音と実スピーカー出力を1つの録音に入れ、波形で入力〜出力遅延を計算する。
- 方式、端末組合せ、会場Wi-Fi/テザリング、IVS併用有無をランごとに切替・記録する。
- 端末が足りない場合に備え、WebRTC接続・負荷・ログ形式を検証する合成クライアントを用意する。ただし合成クライアントの結果を実機音響試験の代替として扱わない。

| 接続 | 音声方式 | 確認内容 |
| --- | --- | --- |
| 1 mic → 1 speaker | PCM / 音声トラック | 接続、音切れ、再生品質を実機確認。録音から音響遅延を別途分析 |
| 1 mic → 3 speakers | 同上 | 1対多fan-out、出力ごとの再生状態、欠落/underflow |
| 2 mics → 2 speakers | 同上 | 多対多の同時経路、全マイク同時再生、クリッピング、音切れ |
| 3 mics → 1 speaker | 同上 | 多対1 fan-in、ミックス、クリッピング、端末負荷 |
| 1 mic → 5 / 3 mics → 5 speakers | 同上 | 任意の追加端末がある場合の実機拡張。なければ合成接続数の補助確認に限定し、音響判定はしない |
| 1 mic + IVS → speakers | 同上 | 同一MediaStream併用、IVS配信への影響、同一LAN直結の維持 |
| 会場Wi-Fi / テザリング | 対応方式 | 直接接続可否、遅延分布、欠落、再接続 |

端末組合せは手元の実機台数に合わせ、1対多・多対多を実機で確認する。1対5や3対5は必須としない。合成接続は接続処理や容量の補助検証に限り、実機音響結果と別集計にする。

## 完了条件

- 単一のstg PoCで最大3マイク・5スピーカーの枠が機能し、手持ち実機による1対多・多対多の検証ができる。1対5/3対5の実機試験は完了条件に含めない。
- 方式別に入力〜出力の実測と音声品質を記録でき、50 ms目標/60 ms上限の達成・未達を判断できる。
- 各runでrawデータ、条件メタデータ、要約が欠損なくエクスポートされ、CSV/JSONと録音データがrun IDで対応付く。
- 実端末で確認できた組合せと合成負荷の結果を明確に分離する。
- Web/API/共有パッケージのテスト、型検査、lint、buildが通る。主な条件（参加上限、音声フレーム処理、ジッタバッファ、ログ欠落/重複、遅延判定）に対してミューテーションを入れ、対象テストが失敗することを確認して戻す。
- stg deploy gateが通り、デプロイ済みURLで参加/計測画面とエクスポート導線を確認する。
- 結果報告に、実施条件・端末一覧・データ件数・集計・生データ取得先・未検証項目・仕様に対する判定を含める。

## リスクと保留事項

- **実機/録音方法**：外部録音機材はなく、iPhone 2台・iPad 1台・MacBookを役割分担して使う。端末モデル/OSは実測時に記録する。合成負荷では音響遅延を判断できないため、音響録音役を確保できない構成ではその判定を未測定とする。
- **3マイクの加算**：全入力を同時に同じ出力へ送るとピークでクリップしうる。リミッターを含め、単独/同時音声で歪みと聞き取りを測る。
- **15本の直接経路**：Wi-Fi/APのクライアント分離、端末CPU/無線送信、ブラウザのピア接続数で失敗する可能性がある。仕様に沿って実測し、未達なら方式Aまたはアプリ化案を判断材料として報告する。
- **音響測定**：スピーカーと録音機の距離、反射音、録音サンプルレートにより測定値が変わる。配置/録音条件を固定し、波形・算出ロジック・生WAVを保存する。
- **音声保存とプライバシー**：既定では音声自体をAWSへ送らない。録音は端末内で保存/ダウンロードし、ユーザーが明示的に共有しない限りstgへアップロードしない。

## 実行順

1. この計画とユーザー確認事項を確定する。
2. APIシグナリング、音声transport、計測/出力、画面/テストをファイル境界で分担し、Codex Orca workersで並行実装する。すべてのworkerはCLAUDE.md/AGENTS.mdの有無を確認し、存在すれば必ず読み、Claude Codeは使わない。
3. 統合、回帰/ミューテーション試験、最大構成のソフトウェア負荷、stgデプロイを行う。
4. 同じ完成PoCを使って実機で可能な1対多・多対多を測り、結果ファイルと判定をまとめる。
5. stg動作確認用にマイク担当・スピーカー担当の2アカウントを発行する。メールは受信可能なユーザー管理下のアドレスを使い、初期パスワードはコード/ログに残さず安全な方法で渡す。
